# 需求与设计文档方法论

面向产品/系统设计文档的一套可复用流程，与具体技术栈无关。目标：让方案**分类有据、旅程自洽、结构清晰、状态严谨、边界可控、结论可信**。

## 何时使用

- 从零写需求文档、产品方案、系统设计。
- 复审已有方案，找矛盾、缺漏、旧残留。
- 设计涉及状态机、权限、并发、回滚等机制的方案。
- 需要把访谈/对话中的诉求收敛成结构化文档。

## 核心原则

1. **分类驱动，不直接开写**：先判定"是什么系统"，再由属性推导"必须解决的领域"。
2. **每个主张都要有落点**：凡声明"必须考虑 X"，正文必须有真实机制落实，不能只在声明表出现。
3. **以事实为准**：规格对照真实代码/真实约束，不凭概念推演。
4. **审核—修复闭环**：用第三方视角反复挑错，逐条核实、分类、修复、复验。

## 步骤

### 1. 应用分类 → 定位必做领域
- 把系统按属性拆成多维（如协作软件/编排平台/治理系统/知识管理平台）。
- 每类属性 → 必须考虑的领域设计 → 映射到章节。
- **反查**：逐个领域核对"正文是否真有落点"；无落点则补落点或删声明。

### 2. 用户相关 → 走用户旅程
- 从入口到结束，按分支逐条走完整旅程。
- 每个动作必须有**触发者、产物、去向**，并与状态机/接口/角色/结束重开对齐。
- 检查：触发点是否明确？是否违反"系统不自我推进"？旅程与机制章是否各说一套？

### 3. 文档逻辑次序
- 固定叙事链：**为什么做 → 做什么 → 怎么做 → 落地（+集成规格）**。
- 开头给结构索引；每章加定位说明；总览（决策总表）前置为索引。
- 消除重复章节，同一主题只留一处。

### 4. 状态机：有转换、有触点
- **状态转换表**：从→到 / 触发者 / 事件 / 前置条件 / 后端动作。
- 配**状态转换图**，与表一一对应。
- 触点只有两类：**人动作 + 后端事件**；系统不自我推进。
- 覆盖异常路径：失败、超时、取消、回滚、重开；定义状态与计数（如 retryCount）的联动。

### 5. 权威源与一致性
- 明确"谁是权威、谁是派生"（如 Git 权威、DB 派生可重建）。
- 定义并发与幂等：CAS、幂等键、串行化、失败补偿矩阵。
- 术语统一、交叉引用可解析。

### 6. 划定边界（做 / 不做）
- 一期范围 + **明确不支持项 + 回退方案**，防止范围膨胀。

### 7. 规格对照真实实现
- 写集成规格前先读源码/真实接口，确认字段、默认行为、继承语义。
- 发现与假设不符时，回改方案中所有相关表述，不止一处。

### 8. 第三方模型审核
- 让外部模型从"再次审核"角度挑错：新旧残留、声明未落地、实现盲点、边界含糊。
- **逐条核实**（不盲信）→ **分类**（硬矛盾/缺漏/设计取舍）→ **修复** → **复验**。
- 用提问收敛范围与优先级，不擅自扩张。

### 9. 自检与复验（可验证性）
每次改动后：
- 交叉引用解析（所有 X.Y 必须对应真实标题）；
- 图解析（mermaid 逐块解析）；
- 结构与代码块围栏平衡；
- 旧概念/术语残留扫描；
- 全量一致性复读。

### 10. 版本与历史管理
- 只保留最新方案；删除旧版；清除"旧方案/历史对照"残留；命名统一。

## 检查清单

**分类与领域**
- [ ] 系统属性是否穷举分类？
- [ ] 每个"必做领域"是否都有正文落点？落点引用是否准确？

**旅程**
- [ ] 每条用户分支是否端到端走完？
- [ ] 每个动作是否有明确触发者？旅程与状态机/接口/角色是否一致？

**逻辑**
- [ ] 是否遵循"为什么→做什么→怎么做→落地"？
- [ ] 有无重复章节、散落主题？

**状态机**
- [ ] 转换表（从/到/触发者/事件/前置/动作）是否完整？
- [ ] 异常路径（失败/超时/取消/回滚/重开）是否覆盖？
- [ ] 状态图与表是否一致？计数/权限等字段是否与状态联动？

**一致性**
- [ ] 权威源是否明确？并发/幂等/补偿是否定义？
- [ ] 术语、引用、命名是否统一？

**边界与规格**
- [ ] 是否写明"不做什么 + 回退"？
- [ ] 规格是否对照真实实现核实过？

**审核**
- [ ] 是否经过第三方视角审核并逐条闭环？

## 一句话概括

> 分类定领域 → 旅程保自洽 → 次序保可读 → 状态机保严谨（转换+触点）→ 权威源保一致 → 边界保可控 → 源码保真实 → 第三方审核 + 脚本自检保收敛。
