# 需求与设计文档方法论

面向产品/系统设计文档的一套可复用流程，与具体技术栈无关。目标：让方案**分类有据、需求可验收、旅程自洽、结构清晰、状态严谨、决策可复盘、追溯闭环、边界可控、结论可信**。

## 何时使用

- 从零写需求文档、产品方案、系统设计。
- 复审已有方案，找矛盾、缺漏、旧残留。
- 设计涉及状态机、权限、并发、回滚等机制的方案。
- 需要把访谈/对话中的诉求收敛成结构化、可验收的文档。

## 核心原则

1. **分类驱动，不直接开写**：先判定"是什么系统"，再由属性推导"必须解决的领域"。
2. **需求必须可验收**：每条需求都要有可测的验收标准；无法验收的需求不算完成。
3. **决策必须留痕**：关键选择记录选项、决策与后果，写清未选方案及原因。
4. **端到端可追溯**：需求 → 设计 → 验收 → 证据 能一一对上；只在声明表出现不算落实。
5. **以事实为准**：规格对照真实代码/真实约束，不凭概念推演。
6. **审核—修复闭环**：用第三方视角反复挑错，逐条核实、分类、修复、复验。

## 步骤

### 1. 明确目标、成功指标与范围
- Working Backwards：先写"成功的定义 / 衡量指标"和范围，再谈方案。
- 明确非目标（non-goals），并记录关键假设与依赖。

### 2. 应用分类 → 定位必做领域
- 把系统按属性拆成多维（如协作软件/编排平台/治理系统/知识管理平台）。
- 每类属性 → 必须考虑的领域设计 → 映射到章节。
- **反查**：逐个领域核对"正文是否真有落点"；无落点则补落点或删声明。

### 3. 需求条目化 → 质量门 → 验收标准
- 每条需求给唯一 ID，满足单一、无歧义、必要、可实现、可验证（参照 IEEE 29148）。
- 每条需求配**验收标准**：优先 `Given-When-Then`；无可测标准的需求不通过质量门。
- 质量门不通过的需求，不进入设计。

### 4. 用户相关 → 走用户旅程
- 从入口到结束，按分支逐条走完整旅程。
- 每个动作必须有**触发者、产物、去向**，并与状态机/接口/角色/结束重开对齐。
- 检查：触发点是否明确？是否违反"系统不自我推进"？旅程与机制章是否各说一套？

### 5. 决策与备选方案（ADR）
- 每个关键选择记一条 ADR：背景 / 选项 / 决策 / 后果 / **未选方案及原因**。
- 只写结论、不写备选与取舍，视为决策未完成。

### 6. 文档逻辑次序
- 固定叙事链：**为什么做 → 做什么 → 怎么做 → 落地（+集成规格）**。
- 开头给结构索引；每章加定位说明；总览（决策总表）前置为索引。
- 消除重复章节，同一主题只留一处。

### 7. 状态机：有转换、有触点
- **状态转换表**：从→到 / 触发者 / 事件 / 前置条件 / 后端动作。
- 配**状态转换图**，与表一一对应。
- 触点只有两类：**人动作 + 后端事件**；系统不自我推进。
- 覆盖异常路径：失败、超时、取消、回滚、重开；定义状态与计数（如 retryCount）的联动。

### 8. 权威源与一致性
- 明确"谁是权威、谁是派生"（如 Git 权威、DB 派生可重建）。
- 定义并发与幂等：CAS、幂等键、串行化、失败补偿矩阵。
- 术语统一、交叉引用可解析。

### 9. 追溯矩阵
- 维护 **需求 ID ↔ 设计章节 ↔ 验收标准 ↔ 证据/测试** 的映射表。
- 任何一方缺失即视为未闭环；新增/删除需求时同步更新矩阵。

### 10. 划定边界（做 / 不做）
- 一期范围 + **明确不支持项 + 回退方案**，防止范围膨胀。

### 11. 规格对照真实实现
- 写集成规格前先读源码/真实接口，确认字段、默认行为、继承语义。
- 发现与假设不符时，回改方案中所有相关表述，不止一处。

### 12. 第三方模型审核（形式化）
- 多视角挑错：功能 / 边界 / 安全 / 可运维；可用红队对抗与 pre-mortem（事前验尸）。
- 问题**分级**（阻断 / 重要 / 建议），要求**引用证据**，逐条核实、分类、修复。
- 关键方案需明确签署（sign-off）。

### 13. 自检与复验（可验证性）
每次改动后：
- 交叉引用解析（所有 X.Y 必须对应真实标题）；
- 图解析（mermaid 逐块解析）；
- 结构与代码块围栏平衡；
- 旧概念/术语残留扫描；
- 全量一致性复读。

### 14. 版本与历史管理
- 只保留最新方案；删除旧版；清除"旧方案/历史对照"残留；命名统一。

## 检查清单

**目标与分类**
- [ ] 成功指标与范围是否明确？非目标是否写清？
- [ ] 系统属性是否穷举分类？
- [ ] 每个"必做领域"是否都有正文落点？落点引用是否准确？

**需求与验收**
- [ ] 每条需求是否有唯一 ID 且单一、无歧义？
- [ ] 每条需求是否有可测的验收标准（Given-When-Then）？
- [ ] 是否过了需求质量门？

**旅程**
- [ ] 每条用户分支是否端到端走完？
- [ ] 每个动作是否有明确触发者？旅程与状态机/接口/角色是否一致？

**决策**
- [ ] 关键选择是否都有 ADR（选项/决策/后果/未选原因）？

**逻辑**
- [ ] 是否遵循"为什么→做什么→怎么做→落地"？
- [ ] 有无重复章节、散落主题？

**状态机**
- [ ] 转换表（从/到/触发者/事件/前置/动作）是否完整？
- [ ] 异常路径（失败/超时/取消/回滚/重开）是否覆盖？
- [ ] 状态图与表是否一致？计数/权限等字段是否与状态联动？

**一致性**
- [ ] 权威源是否明确？并发/幂等/补偿是否定义？
- [ ] 术语、引用、命名是否统一？

**追溯**
- [ ] 需求 ↔ 设计 ↔ 验收 ↔ 证据 是否闭环？矩阵是否最新？

**质量与风险**
- [ ] 非功能需求（性能/安全/可靠/可维护/可运维/成本）是否覆盖？
- [ ] 假设、风险、开放问题是否有台账与处置？
- [ ] 是否做了安全/隐私视角（如滥用用例）？
- [ ] 是否有统一术语表？

**边界与规格**
- [ ] 是否写明"不做什么 + 回退"？
- [ ] 规格是否对照真实实现核实过？

**审核**
- [ ] 是否经过第三方视角审核、分级并逐条闭环？是否已签署？

## 建议产出的工件

- 需求清单（带 ID + 验收标准）
- ADR 集（架构决策记录）
- 追溯矩阵（需求↔设计↔验收↔证据）
- 风险 / 假设 / 开放问题台账
- 术语表（ubiquitous language）

## 一句话概括

> 目标定方向 → 分类定领域 → 需求可验收 → 旅程保自洽 → 决策留备选 → 次序保可读 → 状态机保严谨（转换+触点）→ 权威源保一致 → 追溯保闭环 → 边界保可控 → 源码保真实 → 第三方审核 + 脚本自检保收敛。
