# reqdoc 系统上下文与现有能力规约

## 1. 撰写 PRD 前须先掌握现有系统能力

PRD 中的接口、字段、流程必须建立在「现有系统能做什么」之上，而非凭空设想。需求发起单位的技术侧（或需求分析师）应将系统架构、现有能力、对外接口、数据模型等材料投放至项目根 `05_系统现状与能力/` 目录（可选；未投放则走对话确认，缺口标 `[缺省]`）。

## 2. 先扫后写

若 `05_系统现状与能力/` 目录存在，edge 阶段即调用 `reqdoc_scan(directory="05_系统现状与能力")` 拉取系统上下文，作为 prd 阶段撰写接口/字段/流程的依据；目录不存在则显式向技术侧确认系统能力边界，不自行假设。

## 3. 严禁杜撰系统事实

所有涉及现有系统、接口、字段、能力的陈述，须有 `05_系统现状与能力/` 材料或技术侧确认为依据；未掌握处一律在 PRD 标注 `[缺省/待补系统能力]`，不得编造接口名、字段名或系统行为。

## 4. 与打分卡呼应

系统上下文直接支撑打分卡 `material`（真实接口/字段证据）、`flowClosure`（基于真实系统能力的流程闭环）、`businessValue`（贴合真实系统的价值）三维度；缺系统依据时上述维度如实扣分。

## 5. 逐功能点填写接口与数据源（对应模板 2.11）

模板每个功能点的 `2.11 接口与数据源` 须**逐功能点**说明，不得仅在全局概述里笼统带过：

- 外部系统对接方式：联机/批量/文件，对接哪几个系统、触发方向（本系统调外部 / 外部调本系统）。
- 数据来源系统/字段：上游提供哪些字段、下游消费哪些字段、主键与关联方式。
- 无对接/无来源：须写 `[缺省：本次无外部系统对接]`（带理由，不得裸 `[缺省]`），由 `material` 维度如实扣分。

edge 阶段探针须就每个功能点追问其接口与数据源，确保 `2.11` 不空、不杜撰。
