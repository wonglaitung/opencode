## 1. 问题诊断

### 1.1 同一现实存在五份平行表示

reqdoc 流程里"我们知道什么、还缺什么"被同时记录在五处，每处各有自己的完整性口径：

| # | 表示 | 位置 | 记录内容 | 写入工具 |
|---|------|------|----------|----------|
| 1 | 材料 | 磁盘 `01_背景与目标`~`05_系统现状与能力` + 扫描文本 | 业务投的原始材料 | 业务放文件 → `reqdoc_scan` |
| 2 | probes | `WorkflowState.probes` | 7 探针：问过什么、还缺什么 | `reqdoc_probe` |
| 3 | score | `WorkflowState.score` | 八维得分 + 扣分明细 + 业务确认 | `reqdoc_score` |
| 4 | fieldDict | `WorkflowState.fieldDict` + `数据字典.md` | 字段名/类型/必填/取值/来源系统 | `reqdoc_field_dict` |
| 5 | render + provenance | `WorkflowState.render` / `.renderProvenance` + PRD 正文 | 逐字段填没填、来源标了什么 | `reqdoc_render_skeleton` + `reqdoc_patch` + `reqdoc_check` |

### 1.2 规则库大半在做对账

五份表示必须互相对齐，于是产生一整族一致性规则与校验函数：

- probes ↔ score：报缺口却打满分 → `probeGapViolations`（reqdoc-r21 铁律）
- score ↔ render：标 `[缺省]` 的字段对应维度却满分 → `renderGapViolations`
- fieldDict ↔ score：material 维扣分联动 → reqdoc-r31 双门禁
- render ↔ 模板：章节/块数/来源标注 → `renderStructureViolations`（reqdoc-r23）
- render ↔ 文档支撑：全 `[问答]` 无 `[文档]` → `noDocumentSupportViolation`（reqdoc-r24）
- 字段完整性：裸 `[缺省]` → `missingDefaultReasonViolations`；模板一致性 → `consistencyViolations`；可实施性 → `scoreDimZeroViolations`

**这才是"补丁感"的来源**：不是规则写多了，而是维持多份平行账本的一致性，
规则数量必然随维度数相乘增长。当前 reqdoc 规则 32 条、专属工具 12 个、违规校验函数 7 个。

### 1.3 门禁设计诱导过度追问

`score.total ≥ 85` 才能进 prd + 缺口必须问 + 某维 0 分硬拦。对小模型而言：
猜错 = 扣分 = 被门禁拦；追问 = 无成本。**连环追问是激励结构的必然产物，不是模型行为缺陷。**
CRD 被反复问，本质是"知识没有沉淀物"，每次都要从对话历史重新推导。

### 1.4 重构排序的教训

本设计初版按依赖排期（内核 → 工具 → 门禁 → 规则 → 文档），把回归证据当风险项放在末尾。
这是**排序错误**：重构的首要目标是"少问"，而"少问"与"漏问"在指标上完全同形，
没有冻结的"应有开放项清单"就无法自证没有漏问。回归证据是**排期依据**，不是收尾工作。
因此第 4 章为顶层章，第 12 章按可证性而非依赖重排。

## 2. 目标架构

### 2.1 核心洞察：服务器已经能独立产出整篇文档的结构

`buildPrdSkeleton()`（`packages/shared/src/reqdoc-render.ts`）已能用正则重写生成完整骨架
（`5.1→5.k`、功能点名称、优先级块）；`patchSectionBody()` 能按编号定位写入正文与规范来源标签。
模板 schema（`REQDOC_TEMPLATE_CHAPTERS` + `FEATURE_SUB_SECTIONS` + `MAPPED_FIELD_KEYS`）服务器全知道。

即：**服务器有能力和知识产出整篇文档的结构，模型只贡献各小节的文字。**
现状"骨架服务器生成 + 逐节模型 patch + 结构校验"是绕远路。

### 2.2 唯一抽象：填槽位（Slot）

模板 schema 本身就定义了"哪些槽位必填"。模型的全部产出就是**把槽位填上并声明来源**：

```ts
// packages/shared/src/reqdoc-slots.ts（新文件）
export type SlotSource = "文档" | "问答" | "缺省"   // 与 Option A 来源标签同源
export type SlotStatus = "draft" | "confirmed" | "conflict" | "retired"
// draft=AI/记忆起草待确认；confirmed=业务确认；conflict=记忆与材料冲突待裁决；retired=已作废留痕
// 不计入 slotCoverage、不进 PRD 正文（retired 保留痕迹供审计）

export type SlotKind = "prose" | "term" | "field"

export interface ReqdocSlot {
  kind: SlotKind
  /** prose=模板地址（3.1~3.6、4.1/4.2、5.k.1.1、5.k.2.1~2.13、6.1~6.4、7.1/7.2）
   *  term=4.1 + 术语名作子键 | field=5.k.2.1 + 字段名作子键 */
  address: string
  content: string          // prose=正文文本；term/field=结构化定义（见下）
  source: SlotSource
  status: SlotStatus
  ref?: string             // 材料出处（仅本机，不上行汇报）
  reason?: string          // source=缺省 时必填（等价现有裸 [缺省] 门禁，结构内置）
  askCount?: number        // 该槽位被问过几轮（追问终止规则用，见 6.3）
}
```

**五份表示在这一层全部坍缩**——它们本就是"哪些槽位被填、来源是什么"的不同残缺视图：

| 现有表示 | 在 slot 模型中 |
|----------|----------------|
| 术语表 / 模板 4.1 | 一组 `kind="term"` 槽位（`4.1.<术语名>`）；**4.1 的散文正文是它们的聚合视图** |
| 功能点 / `06_功能点` 子目录 | 地址中出现的不同 `k`（`5.k.*`）；功能点数 = distinct k |
| fieldDict / 模板 2.1 / `数据字典.md` | 一组 `kind="field"` 槽位（`5.k.2.1.<字段名>`）；**2.1 散文与 `数据字典.md` 都是它们的两个视图** |
| provenance（Option A 记账） | `slot.source` 本身，原生内建，不再单独记账 |
| 覆盖率 / 开放追问项 | 必填槽位中 `status ≠ confirmed` 的集合 |
| 八维打分 | 必填槽位按 `MAPPED_FIELD_KEYS[].dims` 上卷（映射表已存在） |

**术语与字段是一等槽位，不是散文的解析结果。** 早期草案曾把 4.1 与 2.1 当作
"一个散文槽位 + 事后解析出术语表/数据字典"，这是错的方向：2.1 是散文描述，
从散文反解字段名/类型/必填/取值域必然出错。改为 term/field 槽位后：
字段定义只写一次，2.1 的散文与 `数据字典.md` 都是它的**两个视图**，全链路无解析。

**覆盖判定口径**：`slotCoverage` 的 "filled" **只认 `status="confirmed"`**，
与 `deriveOpenQuestions` 同口径。这条必须写死——否则模型提交一堆 `draft` 就能刷高覆盖率，
`kbGate` 形同虚设。`reason` 缺失的 `缺省` 槽位视为未填。

**4.1（术语）的 confirmed 条件特殊**：它是 `term` 槽位的**容器章节**，
自身不单独存散文；只要**至少 1 条 term 槽位 confirmed** 即视为 4.1 已覆盖。
但**不因此消灭其他术语的提问**——每个未确认术语仍是独立的开放项，
术语维度与槽位覆盖分开计数（否则一条 CRD 会掩盖其余未知术语）。

### 2.3 文档是构建产物，KB 是源

PRD 文档 = `assemble(slots, template)` 的输出。改文档 = 改槽位后重新构建，
不是编辑 md 再校验。"文档与状态不一致"这一整类问题**因结构不可能发生而消除**，
不再依赖校验函数兜底。每个字符可溯源到 `(address, source)`，强于现有的事后篡改检测。

### 2.4 能力边界：「服务器组装」不等于「服务器写内容」

**这条必须写死，否则会被误读成能力倒退**：模型仍然写**全部正文散文**，
只是写进**槽位**而不是写进**文档**。服务器只做三件事——按地址摆位、打来源标签、保证结构。
它生成不了业务语言，也不假装能。

> 这不是能力增强的宣称，而是**能力归位**：结构由服务器负责（它本来就有能力），
> 内容仍由模型负责（它本来就是内容来源）。变化在于两者不再通过"模型手改文档"耦合。

### 2.5 模型的职责收敛为两件事

1. **填槽**：从材料提取 + 回答问题，产出 `(address, content, source)` 列表
2. **确认**：业务点头或纠正

服务器负责：去重合并、必填槽位派生、覆盖率、打分、组装全文、来源标签、结构合法性、
模板外成果（数据字典/权限矩阵/验收用例）投影。

## 3. 记忆分层（跨项目）

### 3.1 为什么需要

方案若只做术语 glossary，只能解决"别再问 CRD"，不解决"工作流越来越懂你"。
但更重要的发现是：**记忆的收益（少问）与风险（漏问）走的是同一个机制**——
`deriveOpenQuestions` 只认 `confirmed`，记忆若能直接置 `confirmed`，
就等于让记忆消灭提问，与 4.3 那个致命项同源。

所以记忆设计不能只讲"怎么记住"，必须讲"**什么时候允许记忆替你省掉一次提问**"。

现有可复用的半成品：

| 现有设施 | 作用域 | 其实是什么 |
|----------|----------|------------|
| `conventions/reqdoc/*.md`（包内基线） | 全组织 | 规范记忆，已是一层 |
| `<projectRoot>/conventions/reqdoc/*.md` | 单项目 | 规范记忆的项目覆盖层（`conventions.ts:91`） |
| `probes.defaultRounds` | 单需求 | 交互信号（业务是否全程点默认），目前只用于 r27 软提示需求真实性——**一个被浪费的偏好信号** |

即：规约侧已实现"基线 + 覆盖"两层，只缺组织级全局层；事实侧只有术语。

### 3.2 四级分层：按污染风险定权限

| 级 | 内容 | 风险 | 权限 |
|---|---|---|---|
| **L1 身份性事实** | 术语释义、机构/系统名称 | 低（不随项目变） | 命中可**直接置 confirmed，消缺口**（消缺口仅在有槽位处成立，即 reqdoc；sdlc 见 3.3.2） |
| **L2 组织性知识** | 现有系统清单、对外接口、产品线 | 中（会随时间变） | 命中**只作 draft**，引用带来源与时效，需本需求确认 |
| **L3 项目性事实** | 字段定义、流程步骤、接口字段 | 高（项目相关） | **禁止提升为全局**，只在本项目 `需求知识库/` 内复用 |
| **L4 交互偏好** | 偏好详细度、常用表述、是否爱省略 | 低但隐私敏感 | 只影响措辞与详略，**不得影响事实内容** |

L2 值得单独说：它收益明确。当前 `5.k.2.11 接口与数据源` 是最常标 `[缺省]` 的字段
（AI 不知道你们行有哪些系统），一份组织级系统/接口清单能直接填上——这是"越来越懂你"里最实在的一块。

L3 不设提升通道是防污染的关键：项目性事实一旦提升为全局就必然串味。

### 3.3 跨工作流共享维度（scope）

记忆**机制共享、内容不共享**，共享的约占 40%：

| 共享 | 说明 |
|---|---|
| 机制 | 存储形态、`origin` 纪律、写入触发原则、污染分级、可见性/遗忘、"引用而非复制"——全部放 `packages/shared`，各工作流工具只做薄包装 |
| L1 术语库 | ✅ 完全共享。一个行内术语就是那个术语：业务写 PRD 与开发看代码遇到的是同一批黑话 |
| L2 系统清单 | ✅ 部分共享（核心系统、中间件两边都要） |

sdlc 专属的约占 60%：

| 记忆 | 价值 | 数据来源 |
|---|---|---|
| **估时校准** | "同类需求你的估时平均低估 2 倍" | **数据已在管道里**：`BaselineEstimate.estimatedHours` + `efficiencyRatio(estimatedHours, durationMs)`（`workflow.ts:710`）现成在算预估 vs 实际，只是从未被用于学习 |
| 技术栈/构建/发布事实 | sdlc-scoped L2 | 对话确认 |
| 协作偏好 | 改动粒度、注释语言、提交粒度 | sdlc-scoped L4 |
| 返工模式 | "这类需求历史上返了 3 次" | 定稿回顾 |

**一条重要的"不要做"**：代码风格**不需要记忆**。缩进/命名/引号风格已由 formatter +
`AGENTS.md` + `conventions/` 强制，再叠一层记忆只会制造冲突源。记忆只记工具管不了的东西。

#### 3.3.1 同名不同义：跨工作流特有的污染形态

`CRD` 在 k8s 语境 = CustomResourceDefinition，在行内 PRD 语境 = 信贷审批部。
**开发者天天泡在 k8s 环境，这个碰撞极易发生**，后果恶劣：reqdoc 会拿共享记忆
自信地断言一串 Kubernetes 名词进交付件。

部分被写入纪律挡住——只有 `origin=restated`（用户亲口纠正）才写入，
从代码符号推断的定义不写，所以"读到 `OrderService` 类名推导出订单服务"不会入库。
**但残余风险真实存在**：用户在 sdlc 对话里确实可能确认一个与 PRD 语境不同的定义。

补两条规则：

| 规则 | 内容 |
|---|---|
| **代码语境不入 L1** | sdlc 写入 L1 须 `originContext: "business" \| "code"`，纯代码标识符语境**不写 L1** |
| **同名不同义是预期情况** | 同 term 存在两条不同 `kind`/`definition` 时**不静默覆盖、不算异常**，按 3.6 冲突裁决交业务判断；`kind` 字段（行业通用/系统口径/内部简称）正是用来区分两者的 |

#### 3.3.2 sdlc 侧记忆设计

sdlc 与 reqdoc 的**根本结构差异**：sdlc 没有模板槽位，因此**没有"缺口"概念**，
记忆**不能消任何东西**。它只能影响两件事——**怎么问**、**怎么分工**。

这条差异必须写死，否则会有人把 reqdoc 的"L1 命中即免问"套到 sdlc 的门禁与审查上：

> **sdlc 记忆不得用于跳过任何门禁、审查或理解确认。** sdlc 的正确性由服务端门禁与
> `comprehension_*` 闭环保证，记忆只影响**措辞与主动性**，不影响**判定**。

##### 数据源：全部是现成采集、从未用于学习

四类均为**观测型**记忆：按 3.5 的分类，它们在**首次成立时须向开发者确认一次**
（"我注意到你反复手工改 X，以后我少动这些文件，可以吗？"），确认后才继续累计；
未确认的观测**只统计不写入**全局记忆——但计数必须**存在项目内**：落
`WorkflowState.pendingObservations?: { key, pattern, count, firstSeenAt, askedAt }[]`
（项目级 DB，`db/index.ts:51` 那个库）。理由：**可见性是这套设计的前提**（3.7），
若连未确认的计数都不留存，开发者无法知道"系统已注意到 5 次、正在等你确认"，
确认提示就成了凭空出现（B2）。`opencode-sm memory list` 同时读全局条目与本项目 pending。


| 记忆 | 现有数据源（实测） | 成立阈值（口径见下） | 用法（只改问法/分工） |
|---|---|---|
| **返工热点** | `quality.iterationByFile`（按文件路径分桶，`tools/quality.ts:92`）+ `firstPassRate` | 同一目录前缀下累计 ≥ 3 次且 `firstPassRate` < 0.6 | "这类文件历史上要改 3 轮，我先给完整实现再自查"——**主动预告**，而非默默反复试 |
| **分工偏好** | open_ide 文件锁事件（SQLite `file_lock` 表） | 同一目录前缀下锁事件 ≥ 2 次 | 开发者反复手工改某类文件 → **少提议**改写那类路径，先问 |
| **拒绝理由** | `comprehension_reject` 的 **feedback 必填**（`tools/review.ts:167`） | 同类语义 feedback ≥ 2 次 | 重复出现的理由（"别在这加注释"/"命名不对"）→ 提升为约束 |
| **估时先验** | `estimatedHours` + `durationMs` → `efficiencyRatio`（`stats.ts:161`，CLI `stats.ts:169` 展示） | 同类需求完成 ≥ 3 次 | 改进**提问**："上次同类你估 8h 实际 20h，这次按多少估？"——**不是新增统计报表** |
| **术语（L1）** | 与 reqdoc 共用同一份 glossary | 仅 `originContext=business` 条目（3.3.1 规则） |

**阈值口径（可实现性约束）**：

| 口径 | 规则 | 理由 |
|---|---|---|
| **目录前缀 = 前两段路径** | `src/legacy/settlement/x.ts` → `src/legacy`（B3） | 取几段没定义会让 `≥3 次` 的判定随实现漂移；固定两段后可预测、可在 CLI 复现 |
| **拒绝理由按规范化文本精确匹配** | feedback 去除标点/空白/大小写后**完全相同**才累加；不同则视为新候选，须各自单独确认（B4） | "语义相似"要么靠规则（做不到）、要么靠模型（与"纯事件派生"矛盾）。把判断权交还开发者：首次遇到即问"以后作为常规约束吗？" |
| **路径含身份信息时降级为目录级** | 记忆条目只存到目录级，不存具体文件名 | 文件名可能含工单号/客户号，跨项目留存是泄露面 |

##### 与 reqdoc 的三处结构差异

| 维度 | reqdoc | sdlc |
|---|---|---|
| **消费方式** | 填槽、消缺口、生成来源标签 | **只改措辞与分工建议**；不改判定 |
| **匹配键** | 材料全文关键词扫描（7.1 的封顶保证依赖此） | **路径 / 阶段 / 文件类型**；条目本就很小（个位数到几十），注入封顶 1~3 条、约 300 字符 |
| **写入信号** | 用户复述术语 | `reject.feedback` / 锁事件 / 反复返工（均为**行为数据**，非显式陈述） |

##### 与规约的边界

返工热点/分工偏好与 `AGENTS.md` / `conventions/` 相邻但**不重叠**：规约说"代码该怎么写"，
记忆说"这个人历史上怎么做"。**冲突时以 `AGENTS.md` / `conventions` 为准**——
与 3.6 规则 4"冲突优先于记忆"同源，规约优先级更高。

##### 派生时机：写时派生

条目在**观测事件发生时就落盘**（写时派生），不采用读时现算。理由：读时现算的条目
无法审计、无法手工编辑、也无法在 `opencode-sm memory` 里列出——而可见性（3.7）是
这套设计的前提。代价是阈值调整需回填历史，由条目自带 `fromProject` + `confirmedAt` 兜
（可重算、可退役）。

##### 不新增目录、不新增工具

四类 sdlc 条目（返工热点/分工偏好/拒绝理由/估时先验）**全部落在 `l4-prefs/`（`scope=sdlc`）**，
不新增目录——它们都是"这个人的工作行为"而非组织知识，故属 L4 而非 L2。
写入全部挂在**现有事件**上（`tool.execute.after` 的按文件迭代计数、open_ide 锁事件、
`comprehension_reject` 的 feedback、`workflow_baseline` 录入），**不需要新的模型工具**，
故第 8 章的工具计数（12 → 8）不变。

##### 示例

**返工热点**｜`iterationByFile` 显示 `src/legacy/settlement/**` 累计 ≥3 轮且一次通过率 0.4
→ 首次确认：「我注意到 `src/legacy/settlement/` 下的文件平均要改 3 轮以上（历史一次通过率 0.4），以后碰到这类文件我先给完整实现再自查一遍，可以吗？」
→ 落盘 `l4-prefs/iteration-settlement.json`：`{ key: "rework_hotspot", pattern: "src/legacy/settlement/**", avgIterations: 3.2, firstPassRate: 0.4, scope: "sdlc", confirmedBy: "developer" }`
→ 下次：**动手前主动预告**，而非默默反复试。

**分工偏好**｜`src/**/repository/**` 锁事件 ≥2 次
→ 首次确认：「你最近两次手工改了 `src/**/repository/` 下的文件，以后这类文件我先问你要不要我来写，还是干脆不碰？」
→ 下次：少提议改写那类路径，先问。

**拒绝理由**｜两次 `comprehension_reject` 的 feedback 均为「这里不要加注释」
→ 首次确认：「你两次拒绝我的片段都是因为『不要加注释』，以后我生成代码默认不加解释性注释？」
→ 下次：影响**生成侧注释风格**，不改任何判定。

**估时先验**｜3 次同类需求估 8h、实际 20h
→ 首次确认：「你最近 3 次同类需求估 8 小时、实际用了 20 小时，平均低估 2.5 倍。这次估多少？」
→ 下次：改进**提问**，不是新增报表。

**术语**｜开发者说「我们说的对账其实是 T+1 轧差，不是实时」
→ 落盘 `l1-glossary/对账.json`（`scope=org`）：`{ term: "对账", definition: "T+1 轧差，非实时", kind: "内部简称", originContext: "business", origin: "restated" }`
→ 下次：正确使用术语。**sdlc 侧术语不消任何缺口**。

##### 风险

分工偏好容易被读成"被监视/被限制"。约束：**记忆只用于"少提议"，不用于"拒绝执行"**；
开发者明确要求时照做。返工数据含文件路径，属敏感——记忆本就不上行（3.4 隐私纪律），本地留存。

#### 3.3.3 scope 用字段表达

不重构成目录树，多一个字段成本≈0：

```jsonc
{ "term": "CRD", "definition": "信贷审批部", "kind": "内部简称",
  "scope": "org",              // org（默认，两工作流共享）| reqdoc | sdlc
  "originContext": "business", // business=当业务/领域概念讨论 | code=纯代码标识符语境
  "fromProject": "信贷系统改造", "confirmedAt": 1756500000000 }
```

L1/L2 默认 `org`；**L4 必须带 `scope`**——业务偏好简洁文档、开发偏好小步提交，
本就该分开，不该混在一个偏好堆里。

> **本期范围**：只落地 reqdoc 侧，但 `scope` 字段与读写服务**从一开始就按共享设计**。
> 以后 sdlc 接入若要拆文件/改 schema 就得做一次迁移——**存储格式的共享成本必须在第一次就付掉**。

#### 3.3.4 技术要求：不进记忆，归规约

用户说"不要用 Vue2，要用 Vue3"时，**记忆设施不写任何条目**（3.5 已定）。
理由：技术选型是**硬约束**，而记忆是"自动学习、仅本机、软提示"的通道——
把最需要强制执行的知识放进最弱的通道是错位。硬约束的归属：

| 效力 | 去处 |
|---|---|
| 组织统一 | 包内 `conventions/<type>/` 基线（`stage:` 门控注入，随包分发） |
| 项目约定 | `<projectRoot>/conventions/<type>/` 或 `AGENTS.md` |
| **个人习惯** | 也不进记忆——它是偏好而非约束，但记进规约会误导队友。**本设计不承接**（见第 14 章未决项） |

> 这条是**明确的范围声明**而非遗漏：插件不自动改写用户的规约文件
> （那是团队共享资产，AI 无权单方面变更）。本轮对话内模型会遵守该要求，
> 跨会话不保留——这是已知取舍，不是缺陷。

### 3.4 怎么存

**按级分目录、按条分文件**：

```
~/.config/opencode/session-mgmt/
  identity.json                # 已有
  memory/
    l1-glossary/<slug>.json    # 术语/机构/系统名（scope=org 为主）
    l2-org/<slug>.json         # 组织知识：系统清单/接口/产品线
    l4-prefs/<key>.json        # 交互偏好（每条自带 scope）
```

**为什么不是 SQLite、不是单个大 JSON**：

| 选型 | 判断 |
|---|---|
| SQLite 表 | ✗ 插件 DB 是**项目级**的（`db/index.ts:51` — `<project>/.opencode/session-mgmt.db`），记忆需跨项目，位置不对 |
| 单一大 JSON | ✗ 一条损坏全丢；无法"删掉一件事"；用户并发编辑易互相覆盖 |
| 按条文件 | ✓ 损坏隔离、可手改、**删文件即遗忘**（用户需要这个动作）、沿用 `conventions/` 目录式先例 |

**隐私靠架构而非纪律**：记忆不进 SQLite，就意味着 `report.ts` 的上送路径**结构上碰不到它**，
不必每次写汇报都记得脱敏。汇报只上行 `WorkflowState` 投影，记忆文件是独立资产。

条目 schema（两类记忆形状不同——L4 不是内容）：

```jsonc
// 事实记忆 L1/L2
{
  "term": "CRD", "definition": "信贷审批部",
  "kind": "内部简称",                 // 复用 conventions/reqdoc/00-术语与命名.md 第 2 条分类
  "origin": "restated",              // restated=用户复述/纠正 | accepted_default=点了默认
  "scope": "org",                    // 见 3.3.3
  "fromProject": "信贷系统改造",       // 引用而非复制：过期可发现
  "confirmedAt": 1756500000000
}

// L2 额外带时效与作用域
{ "systems": [{ "name": "信贷系统", "interfaces": ["CIPS"] }],
  "scope": "org", "lastVerifiedAt": 1756500000000 }

// 偏好记忆 L4：无 address，只影响措辞与详略
{ "key": "detail_preference", "value": "prefer_concise",
  "scope": "reqdoc",                  // L4 必须带 scope
  "evidence": 4,                      // 观察次数，供用户判断可信度
  "origin": "explicit",               // explicit=用户明说 | inferred=推断
  "retired": false }                  // 撤销不删除条目，只标 retired（保留可溯源）
```

`kind` 分类**直接复用 `conventions/reqdoc/00-术语与命名.md` 第 2 条既有区分**：
行业通用缩写（AML/KYC/CIPS/SWIFT/银承）属正常行话、允许使用；仅"内部黑话"
（团队自造/拼音缩写/代称）需要定义。CRD 属后者，AML 属前者——**不新造分类标准**。

### 3.5 什么时候存

**写入时机**分两类，二者都有用户确认环节，只是一个即时、一个延后——**不存在纯静默写入**：

| 类别 | 含义 | 确认时机 |
|---|---|---|
| **陈述型** | 用户主动说出的信息（复述术语、明说偏好、纠正内容、给技术要求） | **即时**：该次对话内即确认 |

> **A5 词汇消歧**：记忆条目的 `origin` 字段取值 `restated`/`accepted_default`/`explicit`/`inferred`（来源类别），与槽位 `status` 的 `confirmed`（状态）是两套词汇。观测型记忆的确认者另记 `confirmedBy`，**不写 `origin: "confirmed"`**——否则同一词在记忆侧与槽位侧含义不同，实现必出 bug。
| **观测型** | 由机器事件派生（仅 sdlc，见 3.3.2） | **首次成立时确认一次**，之后按已确认条目累计 |

| 触发 | L1 术语 | L2 组织知识 | L4 偏好 |
|---|---|---|---|
| `reqdoc_answer` 业务**复述/纠正**了术语 | 立即写（`origin=restated`） | — | — |
| 用户**纠正任意槽位内容**（不限于术语） | 更新该槽位 | 更新该槽位 | 若纠正的是措辞偏好则写 L4 |
| 用户**明说负向偏好**（"别再问我 X"） | — | — | 立即写（`origin=explicit`），被撤销的 L4 条目标 `retired` |
| 用户**明说技术要求**（"这个项目用 Vue3"） | — | — | **不写记忆**——技术选型是硬约束，归规约（见 3.3.4） |
| `reqdoc_answer` 业务**点了默认** | ✗ 不写 | ✗ 不写 | — |
| 业务提到系统/接口名称 | — | 记为**候选**（暂存项目 KB） | — |
| **定稿前**批量回顾 | 汇总候选 → 业务一次勾选确认 | 同左 | 展示当前偏好供修正 |
| 业务明说"以后都这么写" | — | — | 立即写（`origin=explicit`） |
| **记忆内容被业务改正** | 旧条目标 `存疑` + 写新值 | 同 | 同 |
| 记忆与本项目材料冲突 | 不写，冲突交业务裁决 | 同 | — |

sdlc 的写入挂点见 3.3.2：除四个观测型事件外，**sdlc 同样有陈述型写入**——开发者陈述业务概念（受 `originContext` 约束，见 3.3.1）或明说偏好，按上表陈述型规则即时写入。

三条要点：

1. **静默接受不入库**——"点了默认"意味着业务没真的认可，凭什么让下一个需求直接采信。
2. **写入发生在"改"这个动作上**，不是发生在"生成"上。模型生成一条术语不算数，用户纠正它才算数。
3. **定稿时批量确认**是本设计唯一新增的用户动作，且落在用户本来就要确认文档的时刻，
   边际成本接近零——与整个方案"一次确认替代连环追问"的哲学一致。

**被纠正是最有价值的信号**：记忆命中但用户改了 → 说明记忆已过期。
这条路径同时产出"更新"与"标存疑"，是"越来越懂你"真正兑现的地方。

### 3.6 怎么用

读取发生在 `reqdoc_ingest` 合并槽位时（服务端，模型看不见原始记忆），
**由材料驱动**：拿扫描文本做关键词匹配，只返回命中的条目（第 7 章 7.1 说明为何这是封顶机制）。

| 级 | 命中后槽位状态 | 是否消缺口 | 提问形态 |
|---|---|---|---|
| **L1** | `confirmed`（`source=问答`） | **消** | 不问 |
| **L2** | `draft` + 来源/时效标注 | **不消** | 带记忆作默认猜测："上次在信贷系统改造里提到【信贷系统】，是这个吗？" |
| **L4** | **不进槽位** | — | 只影响生成详略与措辞 |

四条硬规则：

1. **L1 是唯一能消缺口的级**。这正是 4.3"少问 vs 漏问"的答案：
   少问必须来自"用户说过一次、且是复述而非默认"的条目。
2. **L2 命中必须仍被问一次**，但把记忆当默认值给出——用户点一下头就行。
   这让高价值组织知识进来，却不冒充本项目证据。
3. **记忆不得让 material 维打满分**。L2 填了 `5.k.2.11` 后该字段算已答，
   但 material 维度照旧扣分——组织知识不是本项目的真实证据。
4. **冲突优先于记忆**。材料里的定义与记忆不一致时不用记忆，显式提示用户裁决；
   同名不同义（3.3.1）走同一裁决流程。静默取记忆是污染的最短路径。

#### 3.6.1 示例

**① L1 术语（唯一消缺口的一级）**｜`reqdoc_answer` 时业务复述 → 立即写（`origin=restated`）

> AI 问「CRD 是什么？」→ 业务答「信贷审批部，我们行里都这么叫」。
> 落盘 `l1-glossary/CRD.json`：
> `{ "term": "CRD", "definition": "信贷审批部", "kind": "内部简称", "scope": "org", "originContext": "business", "origin": "restated", "fromProject": "信贷系统改造" }`
> **下一个需求**：材料出现 CRD → 命中 → `4.1.CRD` 槽位直接 `confirmed`、**消缺口、不问**。

**② 点了默认 → 不写（防污染入口）**

> AI 问「CRD 我理解是信贷审批部，对吗？」→ 业务点「同意默认」→ **不写记忆，下次还会问**。
> 静默接受不入库：业务没真的认可，凭什么让下一个需求直接采信。

**③ L2 组织知识（消不了缺口，但省一次打字）**

> 业务说「这笔交易要过 CIPS，报文走 ESB」→ 记为**候选，暂存项目 KB**，不立即写全局。
> **定稿回顾**：「收集到 2 条系统信息：① CIPS ② ESB，记入组织知识供后续复用吗？」→ 勾选 → 写入 `l2-org/`，带 `lastVerifiedAt`。
> **下一个需求**：`5.k.2.11` 命中 → 落 `draft`（**不消缺口**），带默认猜测问一次：
> 「上次在信贷系统改造里提到【CIPS】，是这个吗？」→ 点头即 `confirmed`。
> 且 L2 填了 `5.k.2.11` **不让 material 维打满分**——组织知识不是本项目证据。

**④ L4 偏好（不进槽位）**

> 业务说「PRD 里别写太多技术细节，我们就看业务逻辑」→
> `{ "key": "detail_preference", "value": "prefer_business_language", "scope": "reqdoc", "evidence": 1, "origin": "explicit", "retired": false }`
> 只影响生成详略与措辞。
> **撤销**：业务说「别再给我推荐默认项了」→ 写新 L4 + 旧的标 `retired`（不删除，留可溯源）。

**⑤ 冲突裁决：两侧都不装（6.4）**

> 记忆 `CRD=信贷审批部`，本次材料写「CRD 由授信管理部负责」。
> 槽位进入 `conflict`：**两侧内容都不装**、不进 PRD、不算覆盖，呈现对照让业务裁决。

**⑥ 停问收口（6.3）**

> 某开放项问满 2 轮未答 → 停问。若有 L2 带进来的 draft → 强制转
> `[缺省：业务未确认；依据 信贷系统改造@2026-09-30]`。
> PRD 保留这段但**诚实标未确认**；未收口则定稿必拦，须 `review_submit(force=true, force_reason=...)`，
> 且**理由必须业务给**，模型不得代填。

#### 3.6.2 两个工作流的记忆对照

| | reqdoc | sdlc |
|---|---|---|
| 写入时机 | 全是**陈述型** → 即时确认 | 4 类**观测型** → 首次成立时确认一次 |
| L1 术语 | `scope=org` 共用，**消缺口** | 同上，但**不消任何东西**（sdlc 无缺口概念） |
| L2 组织知识 | 定稿回顾时勾选确认 | — |
| L4 内容 | 详略 / 措辞 | 分工 / 返工 / 拒绝理由 / 估时先验 |
| 硬约束（技术选型） | 不写，归规约（3.3.4） | 不写，归规约（3.3.4） |
| 能否影响判定 | 仅 L1 影响槽位覆盖 | **一律不能**（3.3.2 红线） |

### 3.7 可见性（信任前提）

**可见性走 CLI，不给模型加记忆查询工具**：用户查记忆，终端敲一条命令比问模型可靠，
也避免模型成为"它自己记得什么"的传声筒。

- `opencode-sm memory list` / `opencode-sm memory forget <term>`——
  CLI 已有 `init`/`stats`/`list`，加子命令自然，且**两个工作流共用**
- 工具返回只带一句"本次引用 N 条记忆，详见 `opencode-sm memory`"，不重复内容
- 组装（`reqdoc_assemble`）返回里附本次记忆引用数与来源项目
- **A6 遗忘语义**：用户"忘掉"某条记忆 = 删文件（覆盖写 `retired: true`）；但若该条目**正被某个
  未完成项目引用**（`confirmed` 槽位由它消缺口），删除后那些槽位来源会悬空。规则：删除时
  扫描本项目 KB，列出**受影响槽位**让用户确认；用户选择"一并作废"则这些槽位转 `retired`，
  选择"保留"则需先把记忆内容回填为项目内 `draft` 再删。**不允许悄悄删掉导致悬空来源。**

L4 涉及个人工作习惯，可见性更不可省："越来越懂你"若变成"你不知道它拿你做了什么"，
反而是负资产。遗忘 = 删文件（3.4）。

### 3.8 时效维护

条目带 `confirmedAt` + `fromProject`；长期未被引用或被标 `存疑` 的，
在 `opencode-sm memory list` 里提示复核。**不自动删除**——那是用户的数据。

## 4. 回归证据与 golden 集（排期依据）

### 4.1 现有评测的能力与缺口

`scripts/eval-rules/`（46 场景）的判定形态只有五种，全部是 rule-based 断言：前三类判行为，后两类判产出：

| 判定类型 | 断言内容 | 是否比对产出质量 |
|----------|----------|------------------|
| `tool` | 调用了 X 工具且参数匹配 | 否 |
| `no_tool` | 未调用 X 工具 | 否 |
| `text` | 回复含关键词（如 `/new`）；`optionsABC` 判定器 | 仅关键词，代码注释自承「口径脆弱,需人工复核」 |
| `score` / `render`（reqdoc 专属） | 八维确定性评分 / `parseRenderStructure` 结构 diff | 只判结构，不判文字质量 |

`fixtures/baseline/*.txt` 是**规则文本快照**（给评测模型读的输入），不是期望输出。

**结论：现有评测能回答"规则被遵循了吗"，不能回答"重构后质量掉没掉"。**
而槽位重构改的正是内容生成机制——恰好是现有断言覆盖最薄之处。

### 4.2 为什么 sdlc 一直没暴露这个缺口

sdlc 的产出是**行为**（走没走对流程），而流程是确定性状态机——阶段迁移、门禁、审查闭环
都在服务端代码里，`tool`/`no_tool` 判定能完整覆盖。模型的角色只是"决定下一步调什么"，
错了会被服务端门禁拦下，不会静默劣化。

**reqdoc 不同**：模型的角色包含**生产内容**。PRD 正文、抽取的事实、术语释义——
这些没有确定性出口，错了不会被门禁拦住，只会安静地变差。
sdlc 不需要 golden 集是因为它不做内容生成；reqdoc 需要，是因为它做。

### 4.3 核心风险：少问与漏问同形

| 风险 | 现有评测能否发现 |
|------|------------------|
| 同一份材料，重构前后组装出的内容漂移/变简略 | **不能**——无输出比对 |
| 槽位 `content` 被小模型输出得偏短 | **不能**——`render` 判定只看结构 |
| **追问变少，但该问的也没问（漏问）** | **不能**——"少问"与"漏问"指标同形 |
| 术语猜错被确认后固化成事实 | **不能** |

第三行是致命项：重构的**首要目标就是减少追问**，而"少问"与"漏问"无法靠现有断言区分。
唯一防线是**冻结的开放项清单做等价性比对**。

### 4.4 三层 golden

**第 1 层 · 确定性 golden（最重要，零模型成本，CI 必跑）**

纯 shared 纯函数 + 冻结输入，直接比对。四个必含用例：

| 用例 | 断言 |
|------|------|
| **CRD** | 材料含 CRD + 全局库有 CRD → `4.1.CRD` **叶子**槽位为 `confirmed` 且**不在开放项里**；容器覆盖由 `containerCovered('4.1')` 判定为真（**不断言 `4.1` 本身有 status**——6.2.1.1 已定容器无状态、永不进开放项） |
| **AML** | 行业通用缩写 → 不产生定义要求（验 `00-术语与命名.md` 分类生效） |
| **猜错固化** | 猜错定义被纠正确认后入 glossary，下次命中且用的是纠正值（防污染回归） |
| **漏问检测** | 与重构前"应有开放项清单"逐地址相等——多一个=少问了（可疑），少一个=漏问了（回归） |

外加两条预算断言（见第 7 章）：注入长度不超预算；工具返回不超批量上限。

> **陷阱警告**：冻结清单必须**从设计意图推导**（模板必填字段 + 探针语义，人工推导后写入），
> **不是跑一遍现实现去录**。否则把当前 bug 固化成基线，漏问检测就变成了"漏问检测不出来"的检测。

**第 2 层 · 组装幂等 golden（确定性，CI 必跑）**

固定槽位 → `assembleDoc()` 输出 md 的**结构指纹**（章节顺序、功能点块数、每块 13 个子小节地址、
来源标签位置）。**不比逐字**（内容是模型产的，会变），只比结构。防组装逻辑回归。

**第 3 层 · 端到端质量对比（需模型端点，人工/夜间）**

同一批真实材料 + 同一模型（`results/` 已有 `deepseek-v4-flash` / `qwen3` 结果可作参照），
重构前后各跑一次，产出并排对比：

- 八维打分对比——继续用 `judge.kind="score"`，**不并入 `slot.source` 派生，保持独立评分**
- 组装出的 PRD 逐节 diff，人工评审"有没有变简略/变啰嗦"
- **追问轮次数对比 + 开放项漏问核查**（少问且不漏 = 成功）

### 4.5 两套开放项清单

记忆加入后，"应有开放项清单"必须分两套，否则无法区分"记忆生效"与"实现有 bug"：

| 清单 | 用途 |
|------|------|
| **无记忆基线** | 清空记忆时的应有集合；阶段 1 验证派生逻辑用它 |
| **有记忆期望** | 同一输入 + 指定记忆条目 → 哪些缺口应消失、哪些必须仍在；验证"L1 消缺口、L2 不消缺口"这条权限线没写错 |
| **冲突场景期望**（C1） | 仅"有记忆"时存在——`conflict` 是记忆与材料并存才有的状态 |

这让"少问"本身变成可测的，而不是靠人感觉。

> C1 的由来：前两套是"无记忆 / 有记忆"二分，但 **conflict 断言属第三类**——它断言的不是
> "哪些缺口该消失"，而是 `conflict` 槽位**不出现在 PRD、两侧内容都不装、且计入未收口项**。
> 没有这套，"静默取记忆优先于材料"这个错误实现不会被任何断言抓到。

### 4.6 跨工作流的欠账

sdlc 同样没有 golden 集，但按 4.2 的分析**它暂时安全**（服务端门禁承担了兜底职责）。
reqdoc 的 golden 体系是第一个消费者；sdlc 的等价物（门禁决策、片段理解）列为后续低优先项，
**本期不扩范围**。设计此体系时应保持对 sdlc 可复用（共享 golden harness），但不强制。

> **与记忆机制的区分**：记忆机制**从一开始就按跨工作流共享设计**（`scope` 字段 + shared 读写服务，3.3），
> 不属于欠账；欠账的只是 golden harness 的 sdlc 侧断言。

## 5. 目录与落盘

KB 落需求资料根下的独立目录，**不占用 00~07 编号、不混入业务投料区**：

```
<需求资料根>/需求知识库/
  知识库.md        # 人可读账本（服务端渲染；首期只读展示，见第 14 章）
  .kb.json         # 机器态（slots），服务端与 md 同源
```

理由：`00~07` 编号语义为"五步编写流顺序"，插不进 08；`01~05` 是业务投料区，
AI 往业务区写会让用户困惑"这是谁的笔记"。独立顶层目录 + 不编号，性质诚实。

`WorkflowState` 增 `kb?: { slots: ReqdocSlot[]; features: ReqdocFeature[]; updatedAt: number }`
（可选字段，首次前缺省；sdlc 恒缺省——与现有 `probes`/`fieldDict` 同形状）。

`retired` 槽位**在 `知识库.md` 中以删除线保留一行**并注明作废理由（B5）。
"只读展示"不等于"只显示当前有效项"——审计需要看见"曾经有过、为何去掉"，
这正是 `retired` 而非物理删除的意义。

`06_功能点/N_名称/` 下的来源摘录与 `07_需求规格产出/` 下的全部内容**同属构建产物**
（由 `kb.features` / `assemble` 投影），不是数据源。业务改文档应改槽位后重新构建；
直接编辑构建产物会被 `review_submit` 的幂等校验发现（9.3）。

**跨项目记忆不在此目录**，存 `~/.config/opencode/session-mgmt/memory/`（第 3.4 节）：
项目 KB 是本需求的权威源，记忆是跨项目的学习资产，两者生命周期与可信度都不同，
物理分开才能保证"删记忆"不会误伤项目数据、"删项目"不会带走组织知识。

## 6. 派生算法（纯函数，shared 内核）

```ts
// reqdoc-slots.ts
export function requiredSlots(features: readonly ReqdocFeature[]): SlotAddress[]
export function slotCoverage(slots, required): { filled, total, pct, byDim: Record<DimKey, number> }
export function kbGate(slots, features, opts): GateResult        // 唯一门禁：覆盖率 + 来源完备
export function deriveOpenQuestions(slots, features, memory): OpenQuestion[]
export function assembleDoc(slots, features, templateText): string
export function kbDigest(slots): string                            // 聚合摘要，注入规则文本
```

要点：

- `requiredSlots` 复用现有 `REQDOC_TEMPLATE_CHAPTERS` + `FEATURE_SUB_SECTIONS` +
  `MAPPED_FIELD_KEYS`，**不重写模板知识**，这是本设计能低成本落地的关键
- `deriveOpenQuestions` 只认 `status=confirmed` 的槽位；`draft` 槽位**不消缺口**
  （否则模型未确认即当已知，重演"自评满分"老问题）
- 记忆命中按第 3.6 节权限表生效：L1 提升为 `confirmed` 并消缺口，L2 落 `draft` 并附默认猜测
- `kbGate` 取代现有 7 个校验函数

### 6.1 阈值不沿用 85

`REQDOC_SCORE_PASS = 85` 对应的是"八维自评均分"，换算成覆盖率后**不等价**：
覆盖率 85% 远比"八维均分 85"严格（多一个小节未填就掉分）。这是**门槛实质变严**。

**首版不沿用 85**：取保守水位并**记录调整依据**，实测后再校准。
`kbGate` 保留 `force` 显式覆盖并留痕，避免存量需求被硬拦死（`force` 的完整语义见 6.5）。

**必填集趋近于零时的守卫（B1）**：三处规则叠加存在"永不可过"与"空文档也算过"两个极端——
`required: false` 容器不进分母（6.2.1.1）+ 必填叶子 < 30 时不判百分比（7.3）
+ 停问项/记忆来源都不计入 material 分子（6.4.1）。定一条：

| 规则 | 内容 |
|---|---|
| **必填叶子数 < 30 时改判"逐项清单"** | 不判百分比，改为逐项核：每个**声明了 `required: true` 的叶子**是否 `confirmed`。此时分母由"叶子总数"变成"声明必填的叶子数"——**声明面收窄，但每一项都必须真填** |
| **必填叶子 = 0 时禁止定稿** | 若所有容器都声明 `required: false`（必填叶子为 0），`kbGate` 直接判定为"需求不可实施"并拦截——空文档不是交付物 |
| **`required: false` 的声明留痕** | 每个 `required: false` 声明连同理由进 `force` 留痕与 CLI，避免"把必填全声明掉"变成默认路径 |

> B1 的由来：不划这条界，"不答问题 + 全声明为空"会产出**一份没有任何必填内容的 PRD**，
> 而覆盖率百分比还显示 100%——这是覆盖率指标最危险的失效模式。

**`kbGate` 的输入边界（A4）**：它只读 `slotCoverage` 的 confirmed 集合——
**L2 记忆带来的 `draft` 不计入分子也不计入分母**（否则记忆会替业务"填满"覆盖率）；
**`required: false` 的容器不进分母**（6.2.1.1 防绕过规则已把这条路锁死）。。

### 6.2 地址空间与聚合规则

term/field 槽位带子键后，地址分两个空间，**必须显式映射**（实测确认，见下）：

| 空间 | 形态 | 出现位置 |
|---|---|---|
| **文档地址** docAddr | 模板键（`3.1`/`4.1`/`6.1`…）或功能点子小节（`5.1.2.1`，**恒 4 段**） | PRD 正文标题、`parseRenderStructure`、`patchSectionBody` |
| **槽位地址** slotAddr | docAddr，或 docAddr + 子键（`4.1.CRD`、`5.1.2.1.客户号`） | 仅 KB / 状态 / 记忆 |

**实测（`packages/shared/src/reqdoc-render.ts`）**：

| 地址 | `isKnownSectionKey` | `isMappedFieldSection` |
|---|---|---|
| `4.1` / `5.1.2.1` / `5.1.2.12` | ✅ | 5.1.2.1 ✅（属 MAPPED） |
| `4.1.CRD` | ❌ | ❌ |
| `5.1.2.1.客户号` | ❌ | ❌ |

即：现有两处正则（`/^5\.\d+\.[12]\.\d+$/` 与 `^5\.\d+\.(\d+)\.(\d+)$`）
**均不接受子键**。这是"未支持"而非"冲突"，处置为：

1. **不修改文档侧解析**——正文永远不含子键，`parseRenderStructure` / 渲染判定逻辑零改动
2. KB 侧新增纯函数 `docAddrOf(slotAddr)`（剥子键）与 `slotSubKey(slotAddr)`（取子键）
3. 新的 KB 解析器替代即将删除的 `isKnownSectionKey`（它当前是模块私有，未导出）

#### 6.2.0 必填集的权威定义（B2）

"哪些槽位必填"在当前实现里**没有权威来源**——`MAPPED_FIELD_KEYS` 只管 10 个"须标来源"的
映射字段，不等于必填集；而阶段 0 的开放项清单又要求"从设计意图推导、不得跑现实现去录"。
两者缺一环，阶段 0 无法成立。

定 `requiredSlots()` 的三条依据（阶段 1 落为纯函数，阶段 0 用它推导清单）：

| 层级 | 依据 | 例子 |
|---|---|---|
| **必填**（`required: true`） | 模板正文的**元信息章 + 必填小节**：`REQDOC_TEMPLATE_CHAPTERS[].meta`（第一、二章）、`sections[]` 全部（3.1~3.6 / 4.1 / 4.2 / 6.1~6.4 / 7.1 / 7.2） | 项目信息、需求概述、术语定义、非功能、验收标准 |
| **必填** | `MAPPED_FIELD_KEYS` 的 10 个映射字段（逐功能点）——它们本就要求标来源，缺了必构成交付缺陷 | 5.k.1.2、5.k.2.1/3/6/7/8/9/11/12 |
| **建议填**（`required: false`） | 其余 `FEATURE_SUB_SECTIONS`（提示信息、其他要求等） | 5.k.2.4、5.k.2.5 |

**5.k.2.1（字段容器）与 4.1（术语容器）特殊**：它们是容器，必填集按**叶子**判定
（6.2.1.1），且各自有 `required: false` 出口。

> B2 的代价与收益：这样定义让必填集**从模板 schema 派生而非人工枚举**，
> 模板演进时必填集自动跟随——这正是"不重写模板知识"（6 章要点）带来的额外好处。

#### 6.2.1 容器型地址的覆盖判定

`4.1`（术语定义）与 `5.k.2.1`（输入要素的检查）是**容器型**地址——其内容由子槽位聚合而来。
统一规则：

| 规则 | 内容 |
|---|---|
| 容器覆盖 = **至少 1 个 confirmed 子项** | 单条 CRD 即可认 4.1 已覆盖；但**其余术语仍是独立开放项**（术语维度分开计数，见 2.2） |
| 字段清单是开放式的 | 模型提议字段集合，服务端不预设"应有几个字段"，故不按数量判覆盖 |
| 叶子型地址按自身 `confirmed` 算覆盖 | 其余 prose 小节（3.x/5.k.1.x/5.k.2.x 除 2.1/6.x/7.x）均属此类 |

#### 6.2.1.1 容器必填、但只聚合不进开放项（选项 B）

**容器型地址（`4.1` 术语、`5.k.2.1` 字段）本身永不进入开放项清单**——
开放项只到叶子（`term` / `field` 槽位）。理由：容器的内容由子项聚合而来，
"请给出术语定义"这种问法无法落盘（无处安放），且会与子项视图冲突。

但容器**仍是必填单位**（正交于"是否为叶子"这一维）：`4.1`/`5.k.2.1` 是模板必填小节，
章节必须有内容。覆盖判定走**聚合**：≥1 个 confirmed 子项即算该容器已覆盖。

| 规则 | 内容 |
|---|---|
| **容器 = 必填 + 聚合** | 必填集分两类：叶子必填（进开放项）＋容器必填（聚合判定，不进开放项）。`4.1`/`5.k.2.1` 属后者 |
| **候选清单来源** | 术语候选 = 材料中疑似缩写/专名（服务端启发式：连续大写串、括注缩写）+ 记忆命中 + 模型 `ingest` 提议；字段候选 = 模型 `ingest` 提议。**服务端不预置清单**（术语与字段都是开放集合） |
| **可为空通道** | 若某容器的候选清单为空，该容器须声明 `required: false` 并给出理由。**否则"本需求无特殊输入字段"的项目永远卡在门禁上** |
| **防绕过（A3）** | `required: false` **仅在候选清单为空时允许**。容器**有候选却声明 `required: false` → 服务端报错**。这条是硬规则：否则"把容器声明为空"就成了压低覆盖率分母、绕开 7.3 护栏的后门 |

> **B 方案解决的冲突**：6.2.0 曾把 `MAPPED_FIELD_KEYS` 全部列为叶子必填（含 `2.1`＝字段容器），
> 与本节"容器不进开放项"直接矛盾——`2.1` 同时是模板必填小节与字段容器宿主。
> 选项 B 把两者拆成正交维度：**"章节必填"由容器聚合判定，"具体字段"是建议填**（有多少填多少）。
> 这最贴合模板实际形态，且不动 `MAPPED_FIELD_KEYS` 的既有语义（Option A 刚建立）。

`reqdoc_answer` 只接受叶子地址；提交容器地址一律报错（8.2 已定的约束在此明确化）。

#### 6.2.1.2 assemble 对空内容与空节的渲染规则（A2）

此前只定义了标签聚合，未定义**内容为空时怎么写**——而停问项、force 放行的 conflict、
未填的映射字段三处都依赖它。定四条：

| 情形 | 渲染 | 标签 |
|---|---|---|
| prose 槽位有 confirmed 内容 | 正常写正文 | 按 6.2.2 聚合 |
| prose 槽位**空**（从未填 / 停问后 draft 已收敛） | **留空标题，正文为空**；不留占位文字 | 该节标 `[缺省：<理由>]`，理由必填 |
| 映射字段（`MAPPED_FIELD_KEYS`）为空 | 同上 | **仍受"必标来源"约束**——空节也须带 `[缺省：…]`，不允许无标签 |
| 容器节全部子项空且 `required: false` | **整节省略**（不渲染标题），在 4.2 业务规则处留一行说明该节无内容 | 无 |

**"留空标题 + 空正文"是唯一允许的降级形态**：不留 `(未填写)` 之类占位文字（会污染交付件），
也不省略标题（会让章节骨架与模板不一致，破坏"结构由服务器保证"的前提）。

#### 6.2.2 聚合来源标签取最弱档

`5.k.2.1` 属 `MAPPED_FIELD_KEYS`（实测：含 `2.1`），故该节**必须标来源**，
而其正文由多个 field 子槽位聚合而成。定规则：

> **聚合标签 = 各子槽位来源的最弱档**（`缺省` < `问答` < `文档`）。
> 只要有任一 field 标 `缺省`，整节不得标 `[文档]`。

这条是必需的——否则 5 个字段里 1 个是 `[缺省]`，整节仍标 `[文档]`，
Option A 的来源保证就被绕过了。同源则取该源。

`4.1` **不在** `MAPPED_FIELD_KEYS`，故术语节不要求来源标签；
term 槽位的来源只存于 KB，用于记忆与审计，不渲染进正文。

### 6.3 追问终止（不能随探针一起消失）

旧设计的轮次上限是**纯规则文本**约束——`workflow.ts:257` 注释写明"追问轮数上限为规则文本
约束（reqdoc-r2「最长 3 轮」），不入状态"，而 r21 的"未达标三档引导"随本次重构删除。
开放项改为服务端派生后，**没有人再管"问了几轮"**：若某个开放项业务一直不答，
流程会无限停在 edge，这正好违背 r2 的原始意图（"避免业务有被质问的挫败感"）。

新机制显式承接该意图，**由服务端执行而非规则文本**：

| 规则 | 说明 |
|---|---|
| **按轮次计，不按调用计** | `askCount` = 连续出现在**不同轮次**开放项返回中的次数。服务端在下一次返回前，把上一轮已展示且仍未确认的槽位 `askCount+1`；同一轮内重复调用 `ingest`/`answer` **不累加**（B1） |
| **问满 2 轮仍未确认即停问** | 该槽位移出开放项清单，**不再出现在任何提问里** |
| 停问项必须显式收口 | 只能由业务确认（`[缺省]+理由`）或 6.5 的 `force` 关闭；**服务端不得自动确认** |
| **停问时的 draft 收敛** | 有 draft 内容 → 强制转 `[缺省：业务未确认；依据 <来源>@<日期>]`（记忆来源写进理由）；无 draft → `[缺省：业务未确认]`。**PRD 中不得出现无来源标签的正文**（`assemble` 的硬不变量） |
| 收口状态可见（封顶） | 状态条**只显计数 + 前 3 项**，其余折叠为"另有 N 项"；`[缺省：理由]` 全文**不进状态条**，只在 `知识库.md` 与 CLI 查（B6，防止 20 项全停问时状态条被理由撑爆） |

> **A1 的关键点**：停问不等于丢弃知识。L2 记忆带来的 draft 仍然进交付件，
> 但**诚实标成"未确认"并写明出处**——这样既保住组织知识的价值，又不破坏来源保证。
> 反之若保留 draft 又标 `[文档]`，Option A 的来源纪律就在这里漏了。

> 这比旧设计更严格：旧设计靠模型自觉遵守"3 轮"，新设计由服务端停止提问，
> 且停问项一定带着"未被确认"的事实痕迹进入交付件，不会因为"问够了"就悄悄消失。

### 6.4 冲突裁决（记忆 vs 材料）

3.5 触发表规定"冲突交业务裁决"，3.6 规定"不用记忆"——但**裁决期间槽位处于什么状态**未定义。
定 `conflict` 状态承接：

| 阶段 | 槽位状态 | 内容 | 是否进 PRD | 是否算覆盖 |
|---|---|---|---|---|
| 检出冲突 | `conflict` | **两侧都不装**（不装记忆的，也不装材料的） | ✗ | ✗ |
| 呈现给用户 | `conflict` | 带对照：记忆版（来源/日期）vs 材料原文 | ✗ | ✗ |
| 裁决=采纳材料 | `confirmed` | 材料内容，`source=文档`；同时**更新记忆**（记忆为陈旧，转 `origin=restated` 重写） | ✓ | ✓ |
| 裁决=采纳记忆 | `confirmed` | 记忆内容，`source=问答`；**材料侧的旧值退役**（转 `retired` 留痕） | ✓ | ✓ |

关键在第一行：**冲突期间两侧内容都不装**。若先装一边再等裁决，PRD 可能带着
未经确认的一侧进入交付件——这正是 Option A 要防的事。裁决入口与停问一样，
由 `reqdoc_answer` 承载（`address` + `source` 即裁决结果）。

### 6.4.1 停问项与 material 维的结构性张力（A3）

6.2.1.2 定下"空节标签为 `[缺省：…]`"，而3.6 规则 3 定"记忆/缺省不得让 material 维满分"。
两者叠加产生一个**结构性后果**：每个停问项都必然拉低 material 维。若同时有若干
`required: false` 容器（6.2.1.1），material 维可能**永远达不到阈值**。

定三条，避免"怎么填都过不了"：

| 规则 | 内容 |
|---|---|
| **material 维只看 `source=文档` 的 confirmed 槽位** | 停问项（`[缺省]`）与记忆来源（`问答`）都不计入 material 维的分子——这是"组织知识不算本项目证据"的延伸 |
| **material 维不设硬门禁** | 只有 `edgeControl`（需求不可实施）等少数维卡门禁；material 维低分**只影响定稿提示**，不拦（6.5 的 force 只在"存在未收口项"时需要，与维度分数解耦） |
| **停问项收口后重算** | 用户 force 定稿后，material 维按实际内容重算并展示，不因 force 而虚高 |

> A3 的由来：不划这条界，"停问 5 项 + 无字段需求"这类组合会**必然卡门禁**，
> 而用户对"我已经说了不想答"的正确预期是"能定稿并看到扣分说明"，不是"被永久拦住"。

### 6.5 force 的统一语义

6.1 与 6.3 都提到 `force`，但一处是 `kbGate` 选项、一处是停问项的关闭手段。
统一为**一个概念、一处入口**：

```
review_submit(force: boolean, force_reason: string, developer_confirmed: boolean)
        └─> kbGate(slots, features, { force, forceReason })
```

| 规则 | 内容 |
|---|---|
| 唯一入口 | `review_submit` 的 `force` 参数；`kbGate` 不再自行决定 |
| **理由必须业务给** | `force_reason` 不得由模型代填（对齐 `reqdoc_score.business_confirmed` 的既有防自评模式）；模型只能在对话中请业务说明 |
| 明确后果 | **只要存在任一未收口项（停问项 / conflict 项），未 force 则门禁必拦**——这是有意的，"用户没答完"就不该放行 |
| 留痕 | force 通过时把 `{force_reason, 未收口项清单, 时间}` 写入状态，CLI 可见 |
| **force 不能"解决" conflict，只能"关闭"** | 被 force 放行的 `conflict` 槽位**内容仍为空**（6.4 两侧都不装），`assemble` 按最弱档把该容器节标为 `[缺省：冲突未裁决]`，**渲染空节**。要真正落内容必须走 6.4 裁决 |

> A2 的关键：force 是"放行"不是"决定"。若 force 能给 conflict 槽位填内容，
> 就等于绕过了 6.4 的"两侧都不装"，PRD 会重新出现无来源标签的正文——
> 这正是 6.3 停问收敛与 A1 硬不变量要防的同一件事。

> A4 的实质问题不是"force 有两个语义"，而是**没写清"用户不答就必然卡门禁"这个后果**，
> 以及**force_reason 由谁写**。两条都写死后，"止烦"不会在门禁处变成新的烦：
> 用户可以选择"我不想答了，直接按现状定稿"，但必须自己说出理由。

## 7. 上下文预算

### 7.1 三条通道，只有三条

磁盘上的记录（槽位 89 个、记忆几百个文件）**不进上下文**。真正进上下文只有三处：

| 通道 | 现状实测 | 增长方式 |
|---|---|---|
| 规则注入 | prd 阶段注入 **6517 字符**（global 2000 + prd 本级 4517） | 随规则条数增长（已失控） |
| 单点事实源摘要 | score 494 / probe 384 / renderTarget 559 | 固定，不随数据增长 |
| 工具返回值 + 对话累积 | 随轮次增长 | **唯一真正无界的通道** |

**记忆增长不构成上下文风险**，前提是读取**由材料驱动**（3.6）：
服务端拿扫描文本做关键词匹配，只返回命中的条目。L1 攒到 300 条，
注入的永远只有本材料出现过的 0~20 条——这是结构性保证，不依赖自觉。

### 7.2 重构本身让上下文净减约 64%

那些一致性规则正是上下文大户：

| 规则 | 字符 | 处置 | 预计 |
|---|---|---|---|
| r23 渲染结构校验 | 1355 | 删除 | 0 |
| r21 打分门禁 + 缺口↔满分矛盾 | 976 | 删除 | 0 |
| r14 分段渲染流程 | 951 | 重写 | ~300 |
| r20 渲染铁律 + 字段映射 | 900 | 降级为生成事实 | ~200 |
| r11 探针清单 | 779 | 重写 | ~250 |
| r24 柔性门禁 | 365 | 删除 | 0 |
| r31 字段定义双门禁 | 379 | 删除 | 0 |
| r33 填槽纪律（新增） | — | 新增 | ~400 |
| kbDigest（新增） | — | 新增 | ~400 |

**光删四条一致性规则省 3075 字符（占 6517 的 47%）**；
r14/r11/r20 瘦身再省约 1880，新增约 800。
**净变化：6517 → 约 2362 字符，减约 64%**（即规则文本从 17 条降到约 15 条但平均长度大减）。

> **实测偏差（P2 补记）**：实际降至 **4369 字符 / 减约 33%**，未达本节预期。差额来自仍然有效的业务规则
> （追问纪律、槽位落位映射、流程图规则）——原预期假设 r14/r20 的渲染铁律可大幅压缩，实际因需
> 保留「内容写到哪个槽位地址」的映射说明而只减半。阶段 3 继续压缩。

### 7.3 真正会增长的是槽位数

| 功能点数 | 槽位数 | 全量地址列表 | 全量正文 |
|---|---|---|---|
| 2 | 44 | 968 字符 | — |
| 5 | 89 | 1958 字符 | 13350 字符 |
| 8 | 134 | 2948 字符 | — |
| 12 | 194 | 4268 字符 | — |

正文（13350 字符 @ 5 功能点）**只在磁盘，永不重发**。危险的是地址列表：
194 个槽位若一次性注入就是 4268 字符，比整份 r20 还大。

**功能点数无上限的后果（C1）**：分批能兜住注入，但 `kbGate` 阈值是**百分比**——
分母随功能点线性膨胀，40 个功能点时"同样质量的文档"反而更容易达标（多填几个
低价值小节就能拉高比例）。定两条护栏：① 必填叶子槽位总数 < 30 时**不判百分比**，
只逐项判"必填项是否全部 confirmed"；② 百分比阈值不随功能点数下调。

### 7.4 五条封顶机制

| 机制 | 做法 | 效果 |
|---|---|---|
| **确认即出上下文** | 槽位 `confirmed` 后其内容**永不再发**，只在填时付一次成本 | 对比现状：r20 的 900 字符映射表**每轮重发** + 模型反复 read 文件 |
| **只注入当前该填的** | 服务端告知"这 5 个地址开着"，不告知"共有 89 个"；每轮 5~8 条 | 成本 O(批次)，不 O(总量) |
| **kbDigest 只给聚合** | 只给计数 + 进度条，**不给地址、不给内容** | 300~500 字符封顶 |
| **记忆只给命中的** | 材料关键词匹配，封顶 20 条 | 与总记忆量无关 |
| **工具返回不回传全文** | `answer` 返回 `confirmed 5.1.2.3(47字)`；`assemble` 返回结构指纹 | 阻断"每次调用回吐整篇 PRD" |

sdlc 侧的注入另计：条目本就很小且按路径/阶段匹配，**封顶 1~3 条、约 300 字符**（3.3.2），
与 reqdoc 的五条机制互不冲突。

**"确认即出上下文"最关键**：它把当前模型的"反复读同一份材料/规则"变成一次性成本。
这也是小模型最吃不消的地方——注意力被重复内容稀释。

### 7.5 封顶必须在工具层强制

12+ 功能点时全量地址列表 4268 字符是真实压力。**封顶必须在工具返回里强制**（分批返回），
不能靠规则文本叮嘱——r14 会被重写成短文本（第 10 章），指望规则约束批量大小不可靠。
第 4.4 节的注入长度与批量上限断言负责把这条钉住。

### 7.6 一条隐藏收益：上下文可重建

KB 落盘意味着**崩溃/重启后可从磁盘重建状态，不必重放对话**。
这给最坏情况的上下文需求封了顶：无论对话累积多长，权威状态始终在 KB 里，上下文可以丢掉重来。
这在现状下做不到——状态在对话历史里。

**"何时丢、怎么丢"必须显式（C3）**：现实中没人会为重建而主动重开会话。
定：① 提供显式 `/reqdoc-rebuild` 动作（从 `.kb.json` 重建状态 + 重注 `kbDigest`，
对话历史保留但标记 stale）；② **不做自动丢弃**——自动丢上下文会在用户没预期时抹掉 nuance，
风险高于它解决的问题。

## 8. 工具契约

### 8.1 保留不动

| 工具 | 说明 |
|------|------|
| `reqdoc_init` | 目录骨架；**必须增建 `需求知识库/`**（A1）——kb 的落盘位置由本工具拥有，否则 `.kb.json` 无处可写。现状 `REQDOC_DIRS` 只到 `07`（`reqdoc-dirs.ts:19`），需改 |
| `reqdoc_scan` | 材料提取（KB 的输入源） |
| `reqdoc_import` / `reqdoc_review_conventions` | 初稿导入与规约初评，与 KB 正交 |
| `reqdoc_export` | md → docx；输入改为 assemble 产物 |

### 8.2 新增

| 工具 | 职责 | 服务端约束 |
|------|------|----------|
| `reqdoc_ingest(slots[], features[])` | 模型从已扫描材料**批量提取**并提交槽位；服务端去重合并、按第 3.6 节匹配记忆、**返回派生开放项（分批封顶）+ 默认猜测 + 覆盖率** | `status` 由服务端强制（模型不能自称 confirmed）；返回条数受 7.4 批量上限约束；仅 reqdoc |
| `reqdoc_answer(address, content, source)` | 逐项填补派生开放项；服务端置 `confirmed`、写 `知识库.md`；按第 3.5 节决定是否写记忆 | 只接受 `deriveOpenQuestions` 给出的地址；返回不回传全文 |
| `reqdoc_assemble(source?)` | 由槽位投影生成整篇 PRD + 模板外成果（数据字典/权限矩阵/验收用例），幂等 | **无覆盖门槛**——组装是纯投影，任何时候都能跑（否则无法预览草稿）；门禁只在 `review_submit` 读 `kbGate` |

`reqdoc_ingest` 支持**分批**：服务器告知"这些地址还开着"，模型填一批再提交，循环。
模型不决定填什么，只填被指定的——这是对小模型最友好的节奏。

**记忆不设模型工具**：可见性与遗忘走 `opencode-sm memory`（第 3.7 节）。
不为记忆新增工具——模型没有回答"我记得你什么"的权威性，那属于用户与 CLI 的关系。

### 8.3 删除

| 工具 | 原因 |
|------|------|
| `reqdoc_probe` | 开放项由服务端派生，无须模型"记录探针"；`probes` 状态随之删除 |
| `reqdoc_score`（写路径） | 打分改服务端派生；模型不再自评，`business_confirmed` 舞步消失（确认由 `reqdoc_answer` 承载） |
| `reqdoc_field_dict` | 并入槽位（2.1 / 5.k.2.1），`数据字典.md` 改投影 |
| `reqdoc_confirm_features` | 功能点由 `reqdoc_ingest` 一并提交，`06_功能点` 子目录服务端建 |
| `reqdoc_render_skeleton` | 并入 `reqdoc_assemble`（骨架本就是服务器生成） |
| `reqdoc_patch` | **连同刚完成的 Option A 记账一并退役**：模型不再向文档写入，来源标签由 `slot.source` 生成 |
| `reqdoc_check` | 结构违规因投影不可能发生；降级为只读覆盖率报告，并入 `assemble` 返回值 |

工具数 12 → 8，其中**模型驱动的写工具 8 → 2**（`reqdoc_ingest` + `reqdoc_answer`）。
CLI 侧新增 `opencode-sm memory`（`list` / `forget`），承接记忆可见性与遗忘（第 3.7 节），
不作为第 9 个工具。

> Option A 记账退役不是否定那项工作：它验证了"模型写文档必然需要 provenance 记账"，
> 而目标架构里 provenance 内建于 `slot.source`，连单独记账都不需要。

## 9. 状态与门禁重构

### 9.2 违规校验函数

`probeGapViolations` / `renderGapViolations` / `renderStructureViolations` /
`missingDefaultReasonViolations` / `consistencyViolations` / `noDocumentSupportViolation` /
`scoreDimZeroViolations` —— **7 个全部删除**，收敛为 `kbGate()` 一个。

### 9.3 门禁点

| 门禁位置 | 现状 | 重构后 |
|----------|------|--------|
| `workflow_advance(enter prd)` | score ≥ 85 + business_confirmed + probe 已记录 + probeGap 一致 + fieldDict 非空 | `kbGate` 覆盖率达标 + 必填槽位全部 confirmed（或显式 `缺省+理由`） |
| `review_submit` | 上述全部重算 + 结构复核 + 篡改检测 + 来源支撑 | 重新 `assemble` 后比对槽位摘要（幂等校验），防构建产物被手改；并按 3.5 节触发记忆候选回顾 |

**幂等校验的基准（C2）**：`assemble` 产物内嵌 `kbDigest` 摘要
（`address|status|source|reason|content` 逐槽位规范化后取 SHA-256），写在 PRD 头部 HTML 注释里。
`review_submit` 重算比对，三分支必须分清：

| 比对结果 | 判定 | 处置 |
|---|---|---|
| 摘要相同 | 文档与槽位一致 | ✓ 通过 |
| 摘要不同，**槽位也已变** | 「过期构建产物」 | 提示重新 `assemble`（**不是篡改**） |
| 摘要不同，**槽位未变** | 「产物被手改」 | 拒绝 |

把「过期」误判成「篡改」会惩罚正常迭代；把「篡改」误判成「过期」则门禁形同虚设。

阶段键 `["goal","rules","edge","prd","review"]` **不变**（既定决策 2）。
KB 横切，不挂任何 stage：goal/rules/edge 为采集与填槽期，prd 为组装期，review 为确认成文期。

**风险与对策**：

| 风险 | 对策 |
|------|------|

### 方案 C · 记忆证据换源（I-1 的根治）

I-1 的措辞降级只是**承认**开口，没有堵上——证据仍是模型写的槽位正文。换源后模型写什么都命中不了：

| | 改前 | 改后 |
|---|---|---|
| 证据 | `matchMemory(materialOf(kb.slots.map(s => s.content)))` | `matchMemory(await materialEvidence(root))` |
| 作者 | 模型转述 | 业务投放的 **00~05 材料原文** |
| 否定句 `与 CCB 无关` | 命中 CCB → 免问 | 不命中（材料里没有）→ 照问 |

**三个必须守住的边界**：

1. **`06/07` 绝不作证据**——07 里是组装产物，正由槽位正文生成；拿它当证据等于把自证面挪回原位。
2. **`candidates` 只决定「问什么」**，不参与证据（N-5 已堵）。
3. **状态栏读 `kb.evidence` 快照**——`buildStateBar` 是同步的读不了文件，不同步则状态栏与工具回执开放项口径不一。快照**不写进项目侧 `kb.json`**（否则每次换材料往交付目录塞几十 KB 原文）。

**缓存**：按 `名:mtime:size` 指纹失效（材料被业务替换即重读），有护栏钉住「换材料后旧证据不得残留」。

**同轮修的实测缺口（免问 ≠ 已覆盖）**：材料含 `CLD` 且业务曾复述过 → `4.1.CLD` 被移出「本轮该填」清单却仍是 `draft` → 容器 `4.1` 永无 confirmed 子项 → 进 prd 被「必填容器未覆盖：4.1」拦住，而业务从没被问过、AI 也不知道缺的是它（`r11` 规定「清单是唯一依据」，清单里没有它）。**解卡无需业务参与**：`reqdoc_answer(4.1.CLD, …)` 不要求地址在清单里，直接落定即覆盖。**修法在对抗复审后改过一版**：初版把指令写在回执、状态栏、`r33③` 三处，复审指出三处受众都有问题——回执/状态条会被模型转述给业务（`07-业务口语` 禁用 `reqdoc_answer`/`draft` 等词），`r33③` 只在 edge 注入（goal/rules/prd/review 悬空，且第 4 节禁止引用规则编号），措辞「用材料原文落定」还会诱导 `source=文档` 而**材料里根本没有那句定义**（交付件上做不实溯源）。**现版**：动作指令载于 `reqdoc_ingest` 工具描述（model-only、每次请求都在、不分阶段），回执与状态条只报事实且按业务语言措辞，落定 `source` 一律标「问答」，`r30` 注明不算来源降级。护栏：工具描述/回执/状态条/r33③/r30 五处契约断言 + 跟回执走能解卡且 PRD 标 `[问答]` 的端到端（`p0-adversarial` 累计 60 项）。

#### 验收标准 4 补齐 · 「重组装 diff」—— **已补**

2. 定稿时服务端用同一模板**重投影一次**，与磁盘产物做**行多重集比对**；
3. 不一致即拦截并报出差异行。

**实施中发现并修掉的两个真问题**：

| 问题 | 说明 |
|---|---|
| **按行号比对不可靠** | 单行增删会让后续行整体错位。按位比对把「删一段」报成 10 处「被改」——穷举验证不会漏报（总有行数差）但会大量误报。改用**行多重集**（检出增/删/改三类差异），误报从 10 降到 1。 |

至此验收标准 4「组装出的 PRD 与槽位逐字一致」有了完整语义：**手改必被发现**（20 项护栏测试）。
