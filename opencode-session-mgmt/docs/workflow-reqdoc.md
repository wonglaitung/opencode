## 1. 概述

reqdoc 是**需求分析师**的工作流，核心目标**尽量通过 AI 与流程辅助业务人员写需求**：业务「口述 + 丢材料」，AI 扫描提取 + 按缺口追问补全 + 拆功能点 + **把需求内容填进槽位**，再由服务端投影成 PRD，业务逐项确认。源于《业务需求难点与解决方案》的**四段式渐进引导**（目标与场景 → 主流程与规则 → 边界与异常 → 自动化成文），外加**功能点拆解**（prd 前置）、**槽位知识库门禁**（必填槽位覆盖率，见 5 章）与**业务确认闭环**。

**核心模型：槽位是唯一事实源，文档是构建产物**。同一个现实只存一份——`WorkflowState.kb.slots`；PRD 由纯函数 `assembleDoc(slots, features, templateText)` 投影生成，产物首行内嵌 `<!-- kb-digest: xxx -->` 槽位摘要（`kbDigest`：逐槽位规范化 `address|status|source|reason|content` 后取 SHA-256 前 16 位），定稿时重算比对。**取不到的值不再存状态、也不再自评**：覆盖率、开放项清单、必填集、来源标签全部服务端实时派生。

**三大支柱（设计要点）**

reqdoc 的价值链是「**引导追问（喂入）→ 槽位知识库（事实源 + 门禁）→ 服务端组装（交付）**」，三根支柱缺一不可：

1. **引导追问（输入质量）**：业务口述 + 材料投放后，按服务端派生的「本轮该填」清单补齐缺口（goal→rules→edge，每轮最多 5 问、A/B/C 选项 + 【默认推荐项】、同一需求最长 3 轮）。清单由 `deriveQuestions` 从槽位缺口**实时派生**、随业务答复收敛，**只问还没 `confirmed` 的槽位**——这是「少问」的结构性机制（见 6 章）。
2. **槽位知识库（事实源 + 门禁）**：`kbGate` 只读三个输入（`slots` / `features` / `containers`），判据只有三条——必填**叶子**槽位 confirmed 覆盖率、必填**容器**聚合覆盖（选项 B，见 6 章）、无「未收口项」（停问项 + conflict 项）。`force_kb=true` + `force_reason`（**理由必须业务给，模型不得代填**）可放行。
3. **服务端组装（交付形态）**：结构与来源标签由服务端保证——`reqdoc_assemble` 按《业务需求说明书》模板逐字投影出整篇 md 并归档 `07_需求规格产出/`；**模型不得手写或手工编辑产物**（手写产物缺内嵌摘要，定稿必被拦）。来源标签按**最弱档聚合**（任一子项为 `[缺省]` 则整节不得标 `[文档]`），来源保证无法被绕过。

## 2. 工作流定义

**reqdoc 定义**：需求书工作流（需求分析师角色），核心目标**尽量通过 AI 与流程辅助业务人员写需求**：业务「口述 + 丢材料」，AI 扫描提取 + 按缺口追问补全 + 拆功能点 + 把需求内容提交为**槽位**，由服务端投影成 PRD，业务逐项确认。源于《业务需求难点与解决方案》的**四段式渐进引导**（目标与场景 → 主流程与规则 → 边界与异常 → 自动化成文），外加**功能点拆解**（prd 前置）、**槽位知识库门禁**（`kbGate`，见 5 章）与**业务确认闭环**。审查阶段（`reviewStage="review"`）语义为**业务确认 PRD 要点**（区别于 sdlc 的代码理解确认），复用同一套 comprehension/checklist/review_submit 闭环机制。四清单项（completeness 信息完整 / clarity 表达明确 / edgeCoverage 边界覆盖 / resolution 职责清晰），`hasCommitGate=false`（定稿无 git 门禁）。阶段键 `["goal","rules","edge","prd","review"]`，中文名 目标与场景 / 流程与规则 / 边界与异常 / 需求规格书 / 业务确认（`stagePurpose` 依次为「明确谁在用、解决什么痛点」「理清主流程、字段与数据字典」「补全异常、逆向与权限合规」「按模板渲染需求规格书」「业务逐条确认 PRD 要点」）。prd 阶段产出由 `reqdoc_assemble` 按《业务需求说明书》模板投影（`docs/reqdoc-prd-template.md`，源自 `docs/模版.docx`），逐节标来源 `[文档]/[问答]/[缺省]` 不杜撰；**模型不读模板、不手写产物**（结构与标签由服务端保证，见 7 章）。`resolveWorkflowType` 支持 `"reqdoc"`。结构化规则见 4 章；需求资料目录契约（双通道）见 3 章；槽位数据契约与门禁见 5 章；组装与幂等校验见 7 章；PRD 定稿后经 `reqdoc_export` 导出 Word 交付件（见 8 章、session-management.md 8）。

**理解确认的 reqdoc 语义**：reqdoc 复用通用 ComprehensionRecord 机制（见 session-management.md 3.2）——记录对象为 **PRD 要点**（业务目标/核心字段/异常规则/合规要求）而非代码片段，`file`/`lines` 不填；工具参数名一律保留 `codeSegmentId`（sdlc LLM 契约不变），内部映射到 `id`；`comprehension_confirm` 单次只接受一个要点（防批量走过场）。**确认溯源（P3.10）**：`comprehension_confirm` 的可选 `sourceLabel` / `sourceQuote`（来源标签 + 引用原文或编号）在 reqdoc 定稿时**必填**——已接受要点未回填来源证据则 `review_submit` 被拦（防「凭空认可」）；回填后 best-effort 追加写入 PRD 末尾「## 确认溯源」章节，使交付件本身可追溯。

## 3. 需求资料目录契约（双通道）

reqdoc 面向**业务人员**。业务习惯把现成资料（监管发文、旧流程 Word、Excel 台账）散着给，而非结构化表达。为此约定一套**需求资料目录**：业务「按图索骥」分类投放，Agent 经 `reqdoc_scan` 按目录语义精准检索，扫描结果回填为槽位的 `[文档]` 来源。目录信息不进汇报（见 session-management.md 11）、不占用插件库，仅存在于 Agent 的引导行为与工具里。

该目录由 `REQDOC.rules`（见 4 章）驱动 Agent 落地：目录就绪检查落在 goal 阶段规则（reqdoc-r8，含「00_初稿需求书 已有文件先判定走哪个分支」的两分支判定与**分支二八步调用序**（分支二=改已有需求；分支一=全新流程，目录为空时），并入既有那一次提问、不额外多问一轮），初稿导入落在 reqdoc-r32，增量与参考件红线落在 reqdoc-r35，各阶段扫描映射嵌在 edge/prd 规则（reqdoc-r12/13/14），流程图生成在 reqdoc-r34，覆盖度门禁在 reqdoc-r22。**文档扫描经专用工具 `reqdoc_scan` 执行**（单目录参数、按阶段分步调用），对话补缺沿用渐进引导——「分析文档 + 提问题」双通道。

**目录骨架（00~07 材料区 + AI 工作区 + 知识库）**

- **就绪检查**：进入 goal 阶段时检查 00~07 是否存在；缺失则调用 `reqdoc_init` 搭建骨架（幂等，绝不重建或覆盖业务已放材料），并向业务展示各材料目录绝对路径、说明「有多少投多少、未投目录口述补全」，显式提出「投放材料 / 直接口述」二选一（详见 reqdoc-r8）；业务拒绝则直接对话式引导。
- **扫描工具**：`reqdoc_scan(directory)` 单目录参数、按阶段分步调用（goal→01、rules→02、edge→03 与 04、prd→06/07 检查已有产出），解析 docx/pdf/xlsx/txt/md/json/csv 等文本类文档。
- **缺失度校验**：扫描后按映射主动反问——`01` 缺失则优先问「系统要解决的核心痛点」；有 `02` 制度却无 `04` 权限则追问「该制度要求不同岗位的权限如何隔离」。
- **功能点拆解**：prd 阶段综合材料 + 问答信息拆功能点清单，业务确认后 `reqdoc_confirm_features` 记录——**它是 `06_功能点/N_名称/` 目录的唯一创建者**（写入来源摘录 + 幂等预建 `07_需求规格产出/N_名称/`），符合「AI 引导人决定」哲学。功能点清单同时决定必填槽位集（每功能点 10 个必填叶子 + 1 个必填容器，见 5 章），故功能点一改，槽位必填集随之变。
- **槽位化（唯一事实源）**：每轮问答后必须回写槽位——① 提取到的内容批量 `reqdoc_ingest(slots=[...])`（地址取工具返回的「本轮该填」清单，一次最多 8 项，`status` 服务端强制 draft）；② 业务明确答复的项立即 `reqdoc_answer(address, content, source)` 落定 confirmed；③ 连续 2 轮未确认的项被**停问**并移出开放项清单，此时不得反复追问，应显式收口（`source=缺省` + reason 写明未确认原因）。
- **覆盖度门禁**（详见 5 章）：进入 prd 与定稿两处读 `kbGate`——必填叶子槽位未 confirmed、必填容器未覆盖、存在未收口项（停问/conflict）任一成立即拦截；业务明确「本期确实不涉及」的项用 `reqdoc_answer(source=缺省, reason=...)` 显式收口即可计入覆盖；确实无法补齐且业务坚持不做，`force_kb=true` + 业务给的 `force_reason` 放行。
- **产出归档**：PRD 由 `reqdoc_assemble` 投影生成（单功能点落 `07_需求规格产出/N_名称/PRD.md`，多功能点落 `07_需求规格产出/PRD.md`）；模板外成果（UAT 用例、低保真界面说明、数据字典与库表设计、RBAC 权限控制矩阵与审批流）用 write 写入 `07_需求规格产出` 下对应子目录，并在功能点「5.k.2.10 附件」列出清单与相对路径；**Mermaid 流程图例外**——按 r34 内嵌 PRD 正文 `5.k.2.13`（超长才拆独立文件引用），不再单独落盘 `附_流程图/`；PRD 定稿后经 `reqdoc_export` 导出 Word（.docx）交付件。

**多模态边界（硬约束）**：`reqdoc_scan` 目标部署模型（qwen3.6）为纯文本模型，**不支持读图**。扫描件图片/截图由工具显式降级（返回「无法解析图像，请业务文字描述或提供文本版」），杜绝 Agent 空承诺看图。

**边界（明确不做）**

- **不加图片解析**：多模态能力由模型决定，qwen3.6 无视觉支持时工具层显式降级，不做 OCR 等额外能力。
- **幂等**：目录已存在则不重建、不覆盖业务已放材料；`06_功能点` 重复确认覆盖记录；槽位同地址重复提交即覆盖（服务端强制回 draft，须重新确认）。
- **业务确认后才建**：功能点拆解须业务确认后才调用 `reqdoc_confirm_features`（符合「AI 引导人决定」哲学）。
- **模型不碰文档**：`reqdoc_assemble` 产物是构建产物，业务/AI 改内容一律改槽位后重新组装；手工编辑会被定稿幂等校验拦下。
- **插件不追踪路径**：目录信息不进插件库、不进汇报（见 session-management.md 11），纯本机引导层。
- **实施方案第五节「5 大机制」完整机制不纳入**（已定案，防误判为漏功能）：交互原型双确认（低保真 HTML / 可交互界面草图 + 界面确认门禁）、科技可行性与架构预审（行内 API 资产库比对 / 成本风险提醒与降级建议）、版本变更与 Impact Diff 分析（《需求变更影响评估报告》）、研发平台一键排期（JIRA / 行内研发管理平台 API 自动建单）。仅保留相邻能力：
  - 交互原型：不生成 HTML；低保真界面说明以 r20 写入 `07_需求规格产出/界面草图/` 并列入功能点「5.k.2.10 附件」。
  - Impact Diff：变更留痕走 `workflow_revisit` 回退 + 阶段 `revision++` 版本化（见 session-management.md 3.3），不产影响面报告。
  - 一键排期：需求交付以 PRD 落盘 + 人工流转为准，不做 API 对接。
- **UAT 验收测试用例仅落盘、不设「上线验收唯一标准」门禁**：用例草案已纳入（r20 写入 `07_需求规格产出/测试用例/`），但「业务确认后作为上线验收唯一标准」的机制不纳入——规则层只要求落盘归档，不强制确认门禁。
- **不做 Streamlit 门户 / 行内 UI 组件库 / RAG 知识库**：实施方案阶段推进（Phase 1~3）属组织推广计划，本工程不落地 Web 门户、组件库与 RAG 检索；问答留痕以 `comprehension_ask` 本地可检索库为限（见 session-management.md 5.2）。

## 5. 需求知识库门禁（kbGate，唯一门禁）

**数据契约（`WorkflowState.kb`，`packages/shared/src/workflow.ts`）**：

| 字段 | 内容 |

| `slots` | 槽位数组（唯一事实源）。每项 `{ address, kind: prose\|term\|field, content, source: 文档\|问答\|缺省, status: draft\|confirmed\|conflict\|retired, reason?, ref?, askCount? }` |

| `askCounts` | 地址 → 连续出现在开放项的轮次（追问终止用，`STOP_ASK_AFTER=2`） |

**记忆不在 kb 内（阶段 3 已接线）**：记忆是**独立的文件态**，不进 `WorkflowState.kb`、**不参与 `kbGate` 任何一条判据**（记忆只能影响「问不问」与「措辞」，不能让未确认槽位变成已确认）。`WorkflowState.kb` 里只有一个 `evidence` 字段——那是**材料原文快照**（`materialEvidence(root)` 的产物，喂给同步的状态栏用），不是记忆条目，也不写进项目侧 `kb.json`。落盘在 `~/.config/opencode/session-mgmt/memory/{l1-glossary,l2-org,l4-prefs}/*.json`（按条文件、删文件即遗忘，`SM_MEMORY_HOME` 可覆盖测试路径），读写内核在 `packages/shared/src/reqdoc-memory.ts` 与 `reqdoc-kb.ts`。三条语义（对齐 reqdoc-r11 / r27 / r33）：

- **L1 术语命中免问**——业务复述过的内部简称/行业通用词直接采信，不再追问（`deriveQuestions` 的 `l1Applied`，工具返回与状态条都会报「已采信历史记忆 N 项」）。**免问 ≠ 已覆盖**：该项被移出清单却仍是 `draft`，若模型守「清单是唯一依据」而不落定，必填容器 `4.1` 永无 confirmed 子项、进 prd 被拦——**解卡不需业务参与**，但得让 AI 知道该动手。**动作指令载于 `reqdoc_ingest` 的工具描述**（model-only、每次请求都在、不分阶段、从不进时间线），回执与状态条只报**事实 + 一句受众安全的提示**（如状态条「已采信历史记忆 1 项待你落定（不必再问）：4.1.CLD」——**地址必须带上**，回执一次性、状态条是唯一持久提示，跨轮只剩数量会让模型反查无门；措辞按 `07-业务口语` 第 3 节保持可直接转述：不点工具名、不铺门禁因果）；`r33③` 在 edge 阶段再复述一次。**落定 source 一律标「问答」**——定义出自过往需求中业务的复述，材料只出现该词、并未给出定义，标「文档」等于在交付件上做不实溯源（审计拿标签回材料里搜不到那句话），`r30` 已注明凭记忆落定的术语标 [问答] **不算来源降级**。**匹配的证据是 00~05 材料原文**（`materialEvidence`），不是模型转述的槽位正文——否则模型写一句「与 CCB 无关」也能让 CCB 命中（对抗审查 I-1，方案 C）；
- **L2 组织知识不消缺口**——只作默认值带出（开放项带 `guess`，`from: memory-L2`），仍要业务点头才算确认；
- **静默点默认不入库**——`origin=accepted_default` / `inferred` 一律拒写（`isPollutingOrigin`），错误定义不跨需求传播；写入只发生在 `reqdoc_answer(restated_term=...)`（业务主动复述释义 → L1）与定稿后的 `reqdoc_memory_recall`（业务勾选 → L2/L4）。
- **L1 写入必须带业务原话 `business_quote`（对抗审查第九轮）**——`restated_term.business_quote` 必填，留空按**拒写**处理（`writeL1Term` 返回 `missing_quote`，回执说清真因与出路），**不静默入库**。理由是**污染成本不对称**：L1 命中即免问，而免问项只需模型自己 `reqdoc_answer` 落定（source=问答）、**业务全程不参与**——一条伪造的「业务复述」可以永久消掉未来需求里一个本该问的问题，而旧格式条目里只有模型的释义、无从追查谁说的。这与 `force_kb.force_reason`、`reqdoc_adopt_baseline.confirm_note` 同一原则：**理由/凭据必须来自业务，模型不得代填**；`origin` 由服务端钉死为 `restated`（杜绝「点默认也入库」）只是**必要不充分**——它管住了「凭什么入库」，管不住「业务是否真说过」。凭据原样落库（两端空白裁掉）以备审计，`MemoryTerm.businessQuote` 为 optional，旧条目读取不受影响。

**对抗复审第十轮（评测判据在奖励违规）**：真实评测（关闭思考模式后端点才可用，见 10 章）暴露出四个渲染场景 r18/r19/r23/r24 的判据要求「模型正文里渲染出 PRD、拿五维分」——而规则明令「PRD 由服务端从槽位投影生成，不要手写产物」，评测器又从不执行工具（`ModelOutput` 只有 `text` + `toolCalls`），看不到 `reqdoc_assemble` 的返回。**遵守规则的模型必然失败**：这不是模型不听话，是判据在惩罚合规；加强「不要手写」这条规则反而会让分数下降，`--fail-on-regression` 会因此拦住正确的改动。已按「组装后验证」口径重定义为四件模型职责范围内、且规则要求的动作：r18 齐料 → 交服务端组装；r19 缺料（13% 覆盖/20 开放项）→ 继续收集槽位、不提前组装；r23 改既有内容 → 走 `reqdoc_answer` 再重新组装（顺序门禁 + 禁止整篇重提，否则产物摘要过期、定稿三重校验会拒）；r24 缺料 → 收进槽位，不得用 `comprehension_add` 绕过（实测最隐蔽的失败形态）。为此判定器新增 `sequence`（子序列顺序门禁）与 `tool.forbidTool` 两类判据，均有自检用例。

**第十一轮（代价已解决）**：评测器新增 `EVAL_EXECUTE=1`——真实内存 Store + 临时工作区 + 真实工具实现，多轮把工具结果按协议回灌，最后从 `07_需求规格产出/` **递归**读回组装产物（组装按功能点分子目录落盘，只扫顶层会永远读不到，症状是「模型没渲染」这种把排查引向错方向的假失败）。`render` / `score` 判据改为只认 `artifact`，无产物即判不通过。r18 因此恢复为评分场景，评的是真实产物。配套 `exec-selfcheck.ts`（不调模型）证明链路通、产物含内嵌摘要、判据确实读产物、重复调用能被识别。

执行器踩到的两个坑（都已修）：① 判据只看**最后一轮**的工具调用——期望的调用常发生在更早轮次，26 个 reqdoc 场景里 12 个假失败；② 弱模型在工具回灌后 loop 更凶（r14 连发 25 次 `comprehension_add`），且**把「重复调用」如实回灌并不能让它停下**，只能由执行器检测并停止。

**本机真实评测最终结果（本地 qwen3，`EVAL_DISABLE_THINKING=1 EVAL_EXECUTE=1`，26 场景同口径）**：baseline 旧注入 **12/26 = 46%**，new **19/26 = 73%**。r18 仍失败，但归因明确且正确：模型在该端点上死循环于 `reqdoc_confirm_features`（连发 4 次参数完全相同），走不到 ingest/assemble，因而无产物可评——**这是模型局限，不是指标失真**（执行链路自检已证明产物能正常产出并评分）。

**同口径真实评测结果（本地 qwen3，`EVAL_DISABLE_THINKING=1`，26 场景）**：baseline（旧注入快照）**12/26 = 46%**，new **20/26 = 77%**。九个场景转好（r2/r7/r10/r18/r19/r20/r24/r25/r26），**一个真实回退：r5「前序未完成不 submit」baseline 3/3 → new 0/3**（repeat=3 复核，非噪声）。诊断：规则文本与状态条「提交状态：blocked（未完成：prd、review）」**都在**，但状态条重构后同一事实改用业务语言嵌进长条（原始 JSON → 业务语言），显著性下降，弱模型不再据此收手。该回退归因于**状态条重构本身**（`renderBaseline` 镜像的是重构前快照），非本轮改动；修法需改措辞并重跑 baseline，按 P2 交用户拍板。

**评测已覆盖（r25/r26 一正一反）**：真实模型跑不跑得动这条 Previously 只有工具侧单测证明「不给就拒」，没有证明弱模型会主动给。故新增两个 reqdoc 场景——r25 业务口头复述缩写 → 必须调 `reqdoc_answer` 且 `restated_term.business_quote` **非空**；r26 只是点了「同意默认」→ **不得带** `restated_term`（静默点不入库这条防污染红线的直接探针）。为此两件事是前提：① 判定器补点路径判据 `argsNonEmpty` / `forbidArgsPresent`（原有 `args` 只做 `actual[k] === v` 引用相等，判不了嵌套对象）；② 评测的 `reqdoc_answer` 工具镜像此前是简化版、**根本没有** `restated_term`，模型无从调用，已补齐并与真实工具契约一致（含 `business_quote` 必填）。判据自检见 9.8。

**同名不同义不静默覆盖**：材料/记忆释义冲突时交业务裁决（`writeL1Term` 返回 conflict 提示），且**冲突优先于记忆**——材料有原文就不取记忆。

**地址空间**：prose 槽位地址即模板小节号（`3.1`~`3.6`、`4.2`、`6.1`~`6.4`、`7.1`/`7.2`、`5.k.1.1`、`5.k.1.2`、`5.k.2.3`…`5.k.2.13`）；term/field 槽位带子键（`4.1.CRD`、`5.1.2.1.客户号`）。**必填集从模板 schema 派生，不人工枚举**：章节级必填小节（去 meta 章、去容器）13 个 + 每功能点 10 个叶子（`5.k.1.1` 简要概述 + 映射字段叶子 `1.2`/`2.3`/`2.6`/`2.7`/`2.8`/`2.9`/`2.11`/`2.12`/`2.13`；`2.1` 是容器不入叶子集）——**1 个功能点共 23 个必填叶子 + 2 个必填容器**（`4.1`、`5.1.2.1`），3 个功能点共 43 叶子 + 4 容器。

**容器语义（选项 B）**：`4.1`（术语定义）与 `5.k.2.1`（输入要素的检查）是**必填容器但不计入开放项、也不计入覆盖率分母**，只做聚合判定——「有 confirmed 子项」或「显式声明 `required:false` + 理由」二者之一即可；**有候选子项却声明可为空、或有子项但均未确认，都判为未覆盖**（防绕过，见 `containerDeclViolations`）。

**判据（`kbGate`，`packages/shared/src/reqdoc-slots.ts`）**——只读 `slots` / `features` / `containers` 三个输入，共五条，全过即 `pass`：

1. **必填叶子覆盖率**：`requiredSlots` 中存在 `status === "confirmed"` 槽位的比例 ≥ `threshold`（调用点均传 1，即 100%）。**只认 confirmed**——`draft` 不消缺口，防刷覆盖率。
2. **必填容器覆盖**：`requiredContainers` 全部满足聚合判定（见上）。此项**不受 `force` 影响**——容器没内容也没声明可为空时，`force` 放行不了。
3. **无未收口项**：`deriveQuestions(...).unclosed`（停问项 + `conflict` 项）经过滤后为空。
4. **B1 守卫**：必填叶子数为 0 时直接判「需求不可实施」，**空文档不是交付物**。当前模板下章节级叶子恒为 13 个，故该守卫实际只在模板 schema 变更后可能触发；设计它的目的是防止「把必填全声明掉」这条失效路径。
5. **防绕过校验**：容器声明 `required:false` 却未给理由、或有候选子项仍声明为空 → 违规。同样**不受 `force` 影响**。

**force 的边界**：`force_kb=true` 只放宽第 1 条（覆盖率）与第 3 条（未收口项）两条；第 2、4、5 条是结构性约束，不可用 force 绕过。

**阈值不沿用 85**：`REQDOC_SCORE_PASS=85` 对应「八维自评均分」，换算成覆盖率后不等价（覆盖率 85% 远比「八维均分 85」严格，多一个小节未填就掉分）。重构后门禁取**全覆盖（100%）**，并保留 `force_kb` 显式覆盖以免存量需求被硬拦死；阈值校准仍是待办（设计文档 6.1）。注意 `force` 当前**不落状态留痕**——`force_reason` 只用于报错文案与放行判定，不进 `WorkflowState`、也不进汇报（设计文档 6.5 要求的 `{force_reason, 未收口项清单, 时间}` 留痕尚未实现，见 10 章待办）。

**门禁点（两处硬拦截，均只对 `def.type === "reqdoc"` 生效）**：

| 门禁位置 | 校验内容 |
|---|---|
| `workflow_advance(stage=prd, action=enter)` | `kb` 不存在即拦（须先 `reqdoc_ingest`）；否则按上述五条判定 |
| `review_submit` | 同上五条 + **组装幂等校验**（见 7 章）+ 确认溯源门禁（已接受要点须回填 `sourceLabel`/`sourceQuote`）+ 原有前序阶段/片段/清单校验 |

两处共用 `force_kb` + `force_reason` 放行语义（`force_kb=true` 而未给 `force_reason` 直接报错：**理由必须业务给，模型不得代填**）。`workflow_advance` 另有前置条件清单 `REQDOC_STAGE_PREREQS` 在进入/完成阶段后显式列出，让业务提前看到「进下一阶段前必须满足什么」。

**状态条与汇报投影**：状态条（`buildStateBar`）在有 `kb` 时输出「知识库：必填槽位 X/Y（Z%）；门禁可通过 ✓ / 未就绪：<原因>」与「待确认槽位 N 项（本轮问 M）；已停问 K 项」，未建库时输出「知识库：未建（请先 reqdoc_ingest 提交需求内容槽位）」；prd 阶段系统提示另注入「需求知识库流程」三步指引（kb 缺省时注入「知识库未建」三步）。汇报侧 `stats.ts` 的 `SessionStats.kb = { filled, total, pct }` 取代原 `score` 字段（`score` 保留为 deprecated 且恒为 `null`，仅历史 JSON 兼容）。

**打分卡已退役（但共享导出保留）**：`REQDOC_SCORE_DIMS` / `ReqdocScoreDimKey` / `reqdocScoreRubric()` / `REQDOC_SCORE_PASS` **仍存在**，但**不再是 reqdoc 门禁、不再注入任何 reqdoc 规则文本**（r21 已删），唯一消费者是 `scripts/eval-rules/` 的独立评分通道（`score.ts` 镜像八维扣分标准、`judge.ts` 聚合）——设计文档 4.4 第 3 层明确保留该通道。同理，`renderTargetDigest()`、`buildPrdSkeleton()`、`MAPPED_FIELD_KEYS`、`renderCheckRubric()` 是**组装/模板内部工具，不是门禁**（`buildPrdSkeleton` 被 `assembleDoc` 内部调用；`MAPPED_FIELD_KEYS` 用于必填集与「必标来源」判定；`renderTargetDigest`/`renderCheckRubric` 现已无调用点，保留仅为结构描述复用）。

## 6. 开放项派生（少问的机制核心）

**派生而非枚举**：`deriveQuestions(features, { slots, askCounts, decls, l1?, l2?, candidates? })`（`packages/shared/src/reqdoc-slots.ts`）从「必填叶子中未被 confirmed 占的」+「候选清单中未确认的容器子项」实时算出该问什么，返回四段：

| 返回 | 含义 |
|---|---|
| `all` | 本轮该问的全量（未分批、未剔除停问项）——状态条/调试用，不直接进模型 |
| `batch` | 本轮返回给模型的批次（已剔除停问项，按 `QUESTIONS_PER_TURN` 封顶） |
| `stopped` | 因连续 `STOP_ASK_AFTER` 轮未确认被移出清单的项（**未收口**，门禁会拦） |
| `unclosed` | 未收口项 = 停问项 + `conflict` 项（门禁唯一读入项） |

**两个关键常量（服务端强制，不靠规则文本叮嘱）**：

- `STOP_ASK_AFTER = 2`——同一槽位连续出现在 2 轮开放项后被停问；按**轮次**计（`advanceAskCounts` 每轮调一次），同一轮内重复调用不累加。停问不等于放行：该地址进入 `unclosed`，要么业务确认、要么显式 `source=缺省` 收口、要么 `force` 放行。
- `QUESTIONS_PER_TURN = 8`——每轮最多给模型 8 个地址（封顶在 `deriveQuestions` 的 `batch` 上，服务端强制，模型按此清单分批 `reqdoc_ingest`）。

**容器不逐个追问**：`4.1` 与 `5.k.2.1` 只做聚合判定，永不进开放项（见 5 章选项 B）。只有当调用方显式给出 `candidates`（容器下的术语/字段候选清单）时，容器子项才会以 `4.1.CRD` / `5.1.2.1.客户号` 形态进入开放项——**服务端不预置候选**，且当前门禁/工具/状态条调用点均未传 `candidates`，故线上术语与字段只走聚合判定、不逐项追问。

**记忆机制（阶段 3 已接线；2026 全阶段对抗审查 P0-1 修复前此处曾与代码矛盾——`candidates` 生产零传递，等于死代码，现已接通）**：`deriveQuestions` 支持 `l1`（L1 术语记忆）命中即**消缺口**（内部简称/行业通用不再问）、`l2`（L2 组织知识）命中**不消缺口**但带默认猜测问一次。记忆类型与决策内核在 `packages/shared/src/reqdoc-kb.ts`，读写落盘在 `reqdoc-memory.ts`（`matchMemory` 只返回命中项，**记忆原文不可见给模型**），CLI 侧 `opencode-sm memory list` / `forget` 做可见性与遗忘。**记忆生效的必要条件是 `candidates`**：`deriveQuestions` 的候选分支（`opts.candidates`）是 L1/L2 唯一的消费点，缺了它整段不执行。候选由 `reqdoc_ingest(candidates=…)` 提交（材料中真实出现的术语/字段名，**模型不臆造**）并落进 `kb.candidates`，四个生产调用点均已传入。**调用点已传入 `candidates` 与 `l1`/`l2`**：`reqdoc_ingest` 与 `reqdoc_answer` 的返回（每次回写槽位后按**材料原文**重新 `matchMemory` + 派生）、状态条与 prd 阶段注入块（`prompt.ts`，读 `kb.evidence` 快照），因此线上开放项会随记忆收敛，并输出「🧠 已采信历史记忆，免问 N 项」。**证据 = 00~05 材料原文，06/07 不作证据**（07 是组装产物，拿它当证据等于把自证面挪回原位）；代价是 `[问答]`/`[缺省]` 来源的槽位不参与记忆匹配——记忆只服务材料驱动场景。写入侧只有两处入口（业务主动复述 → L1、定稿勾选 → L2/L4，见 5 章），门禁读入的 `unclosed` 不含记忆项（`workflow.ts` / `review.ts` 的 `kbGate` 调用不传 `l1`/`l2`——门禁口径与「少问」口径刻意分开）。

**追问纪律不变**：`≤5 问/轮`、`A/B/C + 【默认推荐项】`、`≤3 轮`、业务语言（禁纯技术词汇）由 reqdoc-r2 约束；r27 进一步要求连续 2 轮走默认后改为开放式追问、强制给数字与真实举例。少问由**派生**保证（已确认的不再问），不由模型自觉保证。

## 7. 组装与幂等校验（PRD 是投影）

**组装（`assembleDoc`，`packages/shared/src/reqdoc-assemble.ts`）**：纯函数入参 `(slots, features, templateText, { containers })`，模板逐字来自 `buildPrdSkeleton(templateText, features)`（部署包随带 `docs/reqdoc-prd-template.md`，客户端不依赖运行目录有模板文件）。逐节处理规则：

- **正文取值**：优先 `confirmed` 槽位，其次 `draft`；`retired` 槽位不参与渲染（`知识库.md` 中以删除线留痕，供审计）。
- **来源标签（最弱档聚合，`aggregateSourceTag`）**：强弱序 `缺省 < 问答 < 文档`，取子项中最弱档——**只要有任一子项为 `[缺省]`，整节不得标 `[文档]`**；容器节无子项标 `[缺省：本节无内容]`。映射字段即使正文为空也须带标签，非映射字段有内容时省略标签（避免正文噪声）。
- **空内容**：prose 空 → 留空标题、正文为空，标 `[缺省：…]`；容器节全空且声明 `required:false` → **整节省略**（连标题都不渲染），并记入 `omittedContainers` 返回给模型。
- **产物元信息**：首行内嵌 `<!-- kb-digest: xxx -->`；工具返回结构指纹（功能点数、小节数、来源标签处数）、省略的空容器节与摘要，**不回吐正文**。

**幂等校验（定稿三分支）**：产物摘要 = 当前槽位摘要 → **一致**，通过；摘要不同且槽位也已变 → **过期构建产物**，提示重跑 `reqdoc_assemble`；摘要不同而槽位未变 → **产物被手改**，拒绝。把「过期」误判成「手改」会惩罚正常迭代，反之门禁形同虚设。另两条硬拦：产物文件缺失（预期路径由 `kb.features` 推导）拦、**产物无内嵌摘要**拦——否则模型用 write 手写一篇 PRD 就能绕开整个校验。

**Word 交付**：`reqdoc_export(source=PRD md 路径)` 把定稿 md 转 .docx，与源 md 同目录归档（实施方案「标准 PRD (Markdown/Word)」）。定稿后另有三项 best-effort 后处理：回填「第二章 文档变更过程」版本行（初始 1.0 / 重做 1.N）、复制 `PRD_V<N>.md` 到 `00_初稿需求书/` 供下轮迭代、把确认溯源追加到 PRD 末尾。

**装配路径与文件名**：`assembleDir` 决定落盘目录（单功能点 → `07_需求规格产出/N_名称/`；多功能点 → `07_需求规格产出/`），定稿校验的预期路径由 `prdRelPath` 从 `kb.features` 推导并**固定拼接 `PRD.md`**。因此 `reqdoc_assemble` 的 `source` 参数只应留空或传 `PRD.md`——传其它文件名会让定稿校验判为「未找到 PRD 产物」。

**docx 与 md 的维护约定**：`docs/模版.docx` 为权威源，`docs/reqdoc-prd-template.md` 为运行时载体（插件读的是 md；r14/r20 规则文本不引用 docx，避免双权威歧义）。**改 docx 必须同步重渲染 md**，否则「严格逐字遵循」名不副实。

## 10. 评测与质量飞轮

规则遵循度评测**方法论**（run 方式、baseline 冻结纪律、判定方式、关键教训、改动分级决策图）见 session-management.md 13.1 / 13.3 / 13.5 / 13.6；sdlc 场景 s1-s22 见 workflow-sdlc.md 8 章。reqdoc 场景 r1-r24 明细如下（场景集共 46 个，判定类分布：`tool` 25 / `no_tool` 12 / `text` 5 / `score` 2 / `render` 2）。

**场景明细（r1-r24）**

 - **追问纪律与引导闭环**：渐进引导最多 5 问带 A/B/C 选项与【默认推荐项】（r1，`text.optionsABC`）/ 业务确认单要点（r2）/ 进 goal 问基线（r3）/ 回到流程规则走 revisit（r4）/ 前序未完成不 submit（r5）/ edge 追问覆盖 ≥2 类（r6）/ 定稿后提示 /new（r7）/ 业务确认正向定稿（r8）/ 要点未定论不定稿（r9）/ 拒绝后重写（r10）。
 - **双通道与功能点拆解**：资料已放好应 `reqdoc_scan` 扫描分析而非空问（r11）、功能点拆解经 `reqdoc_confirm_features` 确认（r12）、功能点未确认不得直接成文定稿（r13）。
 - **槽位知识库门禁（重构后为槽位版断言）**：进 prd 前先 `reqdoc_ingest` 补齐知识库（r14，`expectTool: reqdoc_ingest`）、知识库未就绪（覆盖率不足）不定稿（r15，`no_tool` 禁 review_submit）、槽位全填但未 confirmed 不定稿（r16）、达标且业务确认后定稿（r17，正向 review_submit）。
 - **评分模式（质量飞轮 P0，`judge.kind="score"`，r18-r19）**：对 PRD 文本做八维确定性评分——材料齐全渲染应高分（r18，`minTotal` + `dimMin` 下限）、缺异常与权限渲染应低分不杜撰（r19，`dimMax` 上限），构造产出度量区分度，供 baseline→new 逐维对比。**评分器是开发期度量工具，与生产期门禁无关**（门禁只认 `kbGate`）。
 - **开放项可测化（槽位版，r20-r22）**：追问答复提交为槽位（r20，`expectTool: reqdoc_ingest`；用户明说「权限材料里真没写」→ 应提交 `[缺省]`+理由而非硬编）、知识库未收口不推进（r21，`no_tool` 禁 `workflow_advance(enter prd)`）、覆盖率达标进 prd（r22，正向 `workflow_advance`）。
 - **渲染结构可测化（`judge.kind="render"`，r23-r24）**：对回复文本里的 PRD 渲染骨架用共享 `parseRenderStructure` 做渲染 diff 判定（与运行时解析同源）——材料齐全结构达标（r23，五章齐全且顺序正确 + 2 功能点块）、缺料仍给全骨架且映射字段标 `[缺省]`（r24，结构版不杜撰）。**r23/r24 启用 `soft` 拆级降权（A3/D7）**：来源标注降为**观察项**——仍解析、仍记录进 detail，但不计通过率；硬判据只留结构骨架（章节齐全/顺序/功能点块数）。该拆级在重构后依然有效，但「来源标注是否达标」在生产期已由服务端 `aggregateSourceTag` 保证，不再依赖模型自觉。

> 完成后提示 /new（r7）与审查全流程（r8-r10）为 reqdoc 侧同口径场景，判定框架见 session-management.md 13.3。

**两条评分通道别混（模型自评 ≠ 产出度量）**

- **生产期门禁（reqdoc 工作流内）**：唯一门禁是 `kbGate`（必填槽位覆盖 + 容器聚合 + 无未收口项，见 5 章），读服务端强制的 `confirmed` 状态，模型无法自评通过。
- **开发期评分（eval 侧）**：`scripts/eval-rules` 的 `scorePrd()`（`judge.kind="score"` 配合 r18/r19）：**确定性产出度量**，不靠 LLM 判卷——按内容专属词表谓词对模型产出的 PRD 文本逐维扣分，供 baseline→new 逐维对比；其扣分标准镜像 `REQDOC_SCORE_DIMS`（shared 内仍在，非门禁）。高分自评却渲染不出对应内容，由产出度量暴露。

判定类归属见 session-management.md 13.3：behavior 类（`tool_use`/`no_tool`/`text`）sdlc 与 reqdoc 共用，output 类（`score`/`render`）**reqdoc 专属**，sdlc 不跑（只走通过率）。

**质量飞轮：把产出度量接进评测，从「过/不过」升级为「0-100 八维数字」**

**使用者：本小节面向应用开发人（科技部研发团队）**——飞轮是**开发期迭代工具**（评测门 / 基线冻结 / 46 场景 / 多模型回归）；业务需求提出人在**生产期**只用 reqdoc 工作流与 `kbGate` 门禁，**从不运行飞轮**。

**先分清「度量对象」与「改进落点」**——质量飞轮直接度量的是**需求书（PRD）质量**（八维 0-100），不是这套应用的代码质量；但飞轮的改进落点是**这套应用「产出高质量需求书」的行为面能力**（规则 / 话术模板 / 上下文注入等模型读进上下文的内容），也不是机制面代码质量：

| 维度 | 谁度量 / 验证 | 对象 |
|---|---|---|
| 需求书质量 | 质量飞轮（PRD 八维分，0-100） | 业务需求书 |
| 应用机制面代码质量（bug / 门禁 / 状态机 / DB） | `bun test` + typecheck + CI | 这套应用本身 |
| 应用行为面能力（规则 / 追问话术 / 注入内容能否让模型产出达标需求书） | 评测门 / 质量飞轮 | 这套应用本身 |

一句话：质量飞轮拿「需求书打几分」这个信号去迭代「AI 代笔写需求书」这套应用——**度量落在需求书，改进落在应用的行为面**；应用机制面代码质量跟它无关，走传统工程验证（行为面/机制面边界见 `plugin-guide/eval-driven-rule-iteration.md` 1 章）。

**行为面改进落点 = 注入模型上下文的内容，具体四类**（飞轮每一轮改的就是这些，不是机制面代码）：

1. **规则文本**（`WorkflowDefinition.rules`，按阶段注入）——如 r11 清单追问与槽位回写纪律、r33 填槽纪律、r22 覆盖度门禁、r24 组装幂等门禁；
2. **工具描述**（`reqdoc_ingest` / `reqdoc_answer` / `reqdoc_assemble` / `reqdoc_confirm_features` 等的 `description`）——模型选工具时读的说明；
3. **状态条**（多行阶段状态块：阶段表头「当前阶段（第 N/Y 步）+ 目的 + 状态」/「知识库：必填槽位 X/Y（Z%）；门禁…」/「待确认槽位 N 项（本轮问 M）；已停问 K 项」行）——随会话注入、替代冗长 JSON；
4. **prd 阶段注入的知识库流程指引**（`reqdoc_ingest` → `reqdoc_answer` → `reqdoc_assemble` 三步 + 「不要手工编辑产物」+ 门禁口径）——组装的依据；**模板全文不再注入对话**，结构由服务端投影保证。

其中 r11 的追问话术模板经 `reqdocProbeRubric()` 单点生成，其余规则为直接文本；工具描述只引用不复述完整 rubric，单点事实源不漂移。

**注意区分「改进落点」与「评测判定口径」**：`scenarios.ts` / `judge.ts` / `run.ts` 等**评测脚本不属于行为面**——它们是对照物/量尺：飞轮改的是上面四类注入内容，用判定口径去量改的效果（通过率 / 八维分）。判定口径改动同样要过评测门（判据变了、结果不可直接对比），但那是「换尺子」不是「改被测内容」。

**别当成「全自动优化」：迭代方式与收敛点**

飞轮的目的确实是「迭代出一套让模型产出高八维分需求书的提示词」，但它**不自动改提示词**——是**人机协同的迭代**，且收敛有界：

1. **不是「一直跑」，是「跑 → 看归因 → 改一处 → 再跑」**：每次迭代跑出基线 → 归因出「哪一维弱、对应哪根支柱」→ 应用开发人改对应规则 / 话术 / 注入内容 → 再跑确认那维回升、其它维不降（六步闭环见 `plugin-guide/eval-driven-rule-iteration.md` 2 章）。
2. **「合适」的范围由两个输入框死**——八维 = 希望需求书达标的维度（业务价值 / 流程闭环 / 异常边界 / 合规脱敏 / 权限隔离 / 素材真实性 / 非功能覆盖 / 可验收性），飞轮只在这八维内迭代，评测脚本看不见的 PRD 质量（业务洞察深度、创新性、可读性）不优化；评测场景集 = 喂进来的业务情况代表，提示词只对场景集覆盖的场景泛化。
3. **防过拟合 + 有收敛点**——多模型验证（本地弱模型 + 远端强模型各跑一遍，机制见 `plugin-guide/eval-driven-rule-iteration.md` 6 章）；收敛判据 = 连续几轮各维分数稳定、回归检测无回退、场景全部达标 → 停手沉淀为冻结基线。

rule-based 布尔断言（session-management.md 13.3）只能回答「这版规则让模型遵循得更好吗」，回答不了「需求书质量高了几分」。而 `scorePrd()` 八维打分本就是质量度量器：**让它对每个场景产出的 PRD 自动评分**，评测就获得——

- **每维数字基线**（businessValue / flowClosure / edgeControl / compliance / authority 等各维多少分）
- **回归检测**（改一条规则后哪一维掉了 → 精确定位改坏了什么）
- **归因**（哪个维度系统性薄弱 → 对应三支柱哪一根、哪条规则）

```mermaid
flowchart LR
    R["改一条规则 / 话术模板 / 注入内容"] --> E["跑 eval（baseline / new 对比）"]
    E --> S["scorePrd() 八维自动评分"]
    S --> C{"对比基线：有维度回退?"}
    C -->|"是"| X["不合入，回退改动"]
    C -->|"否"| A["沉淀资产：新场景 / 新规则进 fixture"]
    A --> R
    X --> R
```

**三支柱各自的可持续动作**

1. **追问（少问的结构）**
   - 现状：追问清单由 `deriveQuestions` 从槽位缺口派生（已 `confirmed` 的不再问，**L1 术语命中消缺口、L2 只作默认值**），`STOP_ASK_AFTER=2` 停问、`QUESTIONS_PER_TURN=8` 封顶由服务端强制；r11 提供追问清单口径与槽位回写要求，r33 约束批量起草 / 一次性确认 / 术语优先取记忆。
   - 自持续：eval 数据里哪类槽位最常被停问/最常返工，就调整该类槽位所在阶段的材料引导（哪些目录该多投）或话术模板；「漏问」靠与冻结开放项清单逐地址比对发现（设计文档 4.4 第 1 层 golden）。
2. **事实源与门禁（可测性）**
   - 现状：`kbGate` 单点判定、覆盖只认 `confirmed`、容器聚合 + 防绕过 + B1 守卫。
   - 自持续：阈值（当前全覆盖）按实测校准并记录依据（设计文档 6.1 为待办项）；补 `force_kb` 留痕（`force_reason` + 未收口项清单 + 时间落 `WorkflowState.kb` 并进汇报，设计文档 6.5）——届时停问率 / force 使用率可作为「追问过细/被硬拦」的量化信号。
3. **模板与组装（交付形态）**
   - 现状：`assembleDoc` 纯投影 + 来源最弱档聚合 + `kbDigest` 幂等校验（一致 / 过期 / 手改三分支）。
   - 自持续：**模板结构已改为从 `docs/reqdoc-prd-template.md` 解析**（`reqdoc-template-schema.ts`），换模板只需改该 md，必填集、开放项、组装、结构校验自动跟随；政策层（哪些子节必填/必标来源/是容器）按**标题**声明在 `reqdoc-template-schema.ts`，模板改了小节标题时由 `unresolvedPolicy` 报出要求人工确认。结构侧由 r23/r24 守。

**落地节奏与优先级**

```
每轮迭代：跑 eval（PRD 八维评分）→ 看八维分数分布 → 归因到三支柱 → 改一处
→ 回归对比 → 通过则沉淀 → 下一轮
```

分支之前），子进程实测四阶段全部出现。同时按仓库既有规约补记：**给用户看的故障提示只能挂状态条**（唯一无条件进 system prompt 的载体）。

**对抗复审第九轮（门禁真因 + L1 凭据）**：② **L1 记忆写入缺业务凭据**：四条写入路径里 `force_kb` 要 `force_reason`、`adopt_baseline` 要 `authorized_by` + `confirm_note`、`reqdoc_memory_recall` 要业务勾选，**只有 `restated_term` → L1 什么都没有**。而 L1 命中即免问、免问项由模型自己落定、业务不再被问——伪造的「复述」可永久消掉未来需求里一个本该问的问题，旧格式条目里只有模型的释义、无从追查谁说的。`origin` 由服务端钉死为 `restated` 是必要不充分：管住了「凭什么入库」，管不住「业务是否真说过」。已按用户拍板加 `business_quote`（业务原话）必填、留空拒写、原样落库备审计；新旧条目读取兼容。

**对抗复审第九轮（门禁真因：漂移是「不可读」的同类残留）**：`workflow_advance` 进 prd 的门禁早就为**模板不可读**备了真因前置文案——必填集为空 → ingest 收不到地址 → 默认文案把人引向死路。但**模板已更换**是同一类死路、同一段代码形状，却没人管：此时必填集按新模板算，已逐项确认过的旧地址**一条都不计入**覆盖率，默认文案仍让模型「用 reqdoc_ingest / reqdoc_answer 补齐」。更坏的是补齐旧地址服务端**照收**（`isValidSlotAddr` 对已入库地址留了后门，见 4.2 攻击面那段），覆盖率却不动——模型反复补齐、反复撞同一堵墙，比直接报错更难查；用户看到的也只是「必填叶子覆盖率 48% < 阈值 100%」这种毫无线索的算式。已新增 `templateGateCauseNotice(kb)`（优先级：不可读 > 已更换 > 无）与 `templateDrift` 同策**只报不自动清**，并接到两处门禁：`workflow_advance`（把原 `templateUnavailableNotice` 分支换成真因优先）与 `review_submit`（此前完全没有真因分支）。两条接线均有实测用例（构造漂移知识库后跑真实工具，断言错误文案含「模板结构已更换」、且**不含**「请用 reqdoc_answer 补齐」这类死路指令），已验证修复前红、修复后绿。

顺带记一条本轮查证的**设计意图**（不是缺陷）：`isValidSlotAddr` 对「地址已在 `kb.slots` 里」的提交放行，是为了让换模板后旧槽位仍可被 `reqdoc_answer` 改写——但这不改变门禁判定（必填集来自新模板），所以「旧地址可提交」与「旧地址不计入覆盖率」两件事并存是有意的，代价就是漂移时的指引必须由门禁显式给出，不能指望模型从覆盖率数字里推出来。

**绑定规约**是按工作流类型组织的机构约定（术语与命名、异常分类、可验证性、范围边界、非功能量化、状态生命周期等），由插件在 **reqdoc 会话**自动送达系统提示（见 session-management.md 7.1 注入通道），**只注入、无门禁**（不参与门禁/评测、不进 `WorkflowDefinition.rules`）。与 sdlc 侧（workflow-sdlc.md 9 章）共用同一套机制，只是目录按类型隔离。**阶段门控**同 sdlc：每个 `.md` 头部 frontmatter 声明 `stage`（`global`=常驻全程，否则仅在对应当前阶段注入；无 in_progress 只注入 global）。两层来源、插件合并：

- **基线（插件打包）**：`packages/plugin/conventions/reqdoc/*.md`。当前：`03-范围与边界`（goal）、`00-术语与命名`/`05-状态与生命周期`（rules）、`01-异常分类`/`04-非功能需求量化`（edge）、`02-可验证性与验收标准`（prd）。
- **机构覆盖（项目内）**：`<项目根>/conventions/reqdoc/*.md`，机构自定义，插件读取后追加到基线之后（类型隔离，不跨工作流泄漏）。

通用/常驻的机构规则（跨工作流适用）写机构自己的 `AGENTS.md`（OpenCode 原生合并），不放本目录。新增 reqdoc 规约 = 往该目录丢一个带 `stage:` frontmatter 的 `.md`，零代码。加载/过滤/拼接见 `packages/plugin/src/conventions.ts`（`loadWorkflowConventions(type, stage, projectRoot)`）。
